# officeace2api

把本机 **OfficeAce（果办 / Office Claw）** 桌面端的模型网关，反代成一套标准的 **OpenAI 兼容 API**，
任何支持自定义 BaseURL 的客户端（Cherry Studio、NextChat、LobeChat、Cline、Roo Code、Continue、
Cursor、Dify、OpenAI SDK…）都能直接接进来用。

- **零依赖**：只用 Node.js 内置模块，不用 `npm install`
- **零配置起步**：自动从本机已登录的 OfficeAce 客户端里找到上游地址和鉴权凭据
- **32 个模型**：GLM-5.3 / GLM-5.2 / DeepSeek-V4.1-Flash / DeepSeek-V4-Pro / Kimi-K2.6 / Qwen3 / openPangu 全系
- **完整协议**：流式 SSE 透传、非流式聚合、Function Calling（工具调用）、reasoning_content 推理内容、usage 统计
- **带控制台**：浅色系后台，7 个菜单装完 12 块内容；看凭据状态、模型清单、一键试模型、实时日志
- **号池 + 积分额度**：多账号聚合、一键授权、批量注册；每个号**还剩多少积分**直接问华为云拿，一眼看懂
- **不用管它**：临时凭据到期自动续期、每天自动签到领积分、进程死了 4 秒内自己爬起来

## 一、原理（它到底"反代"了什么）

OfficeAce 桌面端的模型能力由内置的 `relayclaw` 运行时（jiuwenswarm Agent）提供。这个运行时启动时，
桌面端会把**真实的上游模型网关地址 + 鉴权头**同步到本机磁盘：

```
~/.office-claw/.jiuwenclaw/config/routing_state/users/<账号ID>/models.json
```

文件里每一条模型配置长这样（真实内容）：

```json
{
  "model_client_config": {
    "api_base": "https://modelgw-0004.officeace.cn-southwest-2.huaweicloud-agentarts.com/v2",
    "api_key": "huawei-maas-session",
    "model_name": "deepseek-v4.1-flash",
    "client_provider": "OpenAI",
    "custom_headers": {
      "Authorization": "Basic <AK>:<SK>"
    }
  },
  "model_provider": "huawei_maas"
}
```

也就是说：**上游本身就是 OpenAI 兼容协议**（华为 AgentArts 模型网关，APIG 签名走 Basic AK/SK），
只是藏在桌面的本地文件里。`officeace2api` 做的就是：

```
任意 OpenAI 客户端 ──▶ officeace2api（本机 127.0.0.1:7864）
                          │  1. 自动读取 models.json 里的 api_base + Authorization
                          │  2. 请求体净化 / 重试 / 限流冷却 / 凭据轮换
                          ▼
                     https://modelgw-0004.officeace.cn-southwest-2.huaweicloud-agentarts.com/v2
```

因为凭据是"读本机文件"而不是"中间人抓包"，所以**不需要装证书、不受 HTTPS 证书固定影响**，
OfficeAce 客户端升级只要它还在用同一套机制就照旧可用；凭据被刷新时本服务也会自动重载。

## 二、快速开始

### 1. 前置

- 本机已安装并**成功登录**过 OfficeAce 桌面端，且**至少发起过一次对话**
  （这样 `models.json` 才会被写出来）
- Node.js ≥ 20 —— **通常不用自己装**：启动脚本会自动去找 OfficeAce 自带的
  `node.exe`（`<OfficeAce安装目录>\tools\node\node.exe`，版本 22+）。
  找不到时按顺序回退：`data\node.txt` → PATH 上的 node → OfficeAce 目录 → `Program Files`。
  注意 PATH 上是老版本 Node（14/16）时会被自动跳过，脚本只认 ≥ 20 的。

### 2. 以服务方式安装（推荐，开机自启）

双击 **`install-autostart.cmd`**：它会把程序注册成 Windows 计划任务 `officeace2api`，
由系统的任务计划服务托管进程。好处是**不依赖任何命令行窗口**，关掉窗口、注销、重启都不会掉，
并且每次登录自动拉起。

```
[i] node : D:\软件\OfficeAce\tools\node\node.exe  (v22.22.2)
[OK] scheduled task 'officeace2api' installed
[OK] will start automatically at every logon
[OK] running: http://127.0.0.1:7864/healthz
```

不需要自启了就双击 `remove-autostart.cmd` 卸载。

### 3. 手动启动（临时用）

双击 `start.cmd`：如果计划任务已安装就调它启动，没安装就直接后台拉起进程。

```
[OK] service is up

  OpenAI base : http://127.0.0.1:7864/v1
  Admin panel : http://127.0.0.1:7864/admin
  API key     : sk-officeace
  Log file    : logs\server.log
```

> ⚠️ **别在命令行窗口里直接 `node src/index.mjs` 之后就关窗口** —— 窗口一关进程就跟着死，
> 浏览器打开会看到 `ERR_CONNECTION_REFUSED`。要么双击 `start.cmd`（内部做了分离），
> 要么用 `install-autostart.cmd` 交给任务计划服务。

### 4. 接入客户端

| 项目 | 填什么 |
| --- | --- |
| Base URL / 接口地址 | `http://127.0.0.1:7864/v1` |
| API Key | `sk-officeace`（在 `config.json` 的 `apiKeys` 里改） |
| Model | 见 `/v1/models`，推荐 `glm-5.2` / `deepseek-v4-flash-0731` |

> 有些客户端要求 BaseURL 不带 `/v1`（例如 Cline 填 `http://127.0.0.1:7864`），
> 两种都能用，本服务的路由是 `/v1/...`，客户端会自动补。

### 5. 验证

```bash
# 列模型
curl http://127.0.0.1:7864/v1/models -H "Authorization: Bearer sk-officeace"

# 非流式
curl http://127.0.0.1:7864/v1/chat/completions \
  -H "Authorization: Bearer sk-officeace" -H "Content-Type: application/json" \
  -d '{"model":"glm-5.2","messages":[{"role":"user","content":"你好"}]}'

# 流式
curl -N http://127.0.0.1:7864/v1/chat/completions \
  -H "Authorization: Bearer sk-officeace" -H "Content-Type: application/json" \
  -d '{"model":"deepseek-v4-flash-0731","messages":[{"role":"user","content":"数到5"}],"stream":true}'
```

项目自带自测脚本：`node tools/smoke-test.mjs`（自动跑一遍非流式 + 流式）。

## 三、可用模型（34 个）

> ⚠️ 这 34 个是**上游网关的目录**，不等于"每个都打得通"。
> 实测两个号的时候只有 **11 个**真的能用，其余 23 个上游回 `81004`（没权限）或 `81009`（名字不认）。
> 那部分模型默认**不再列在 `/v1/models` 里**（`config.models.hideUnavailable: true`），
> 打过去会立刻收到 400 `model_not_available`，面板「模型管理」上会把它们的名字列出来。
> 详见「七之三之二 · 坑三」。
>
> ⚠️ 能用的那 11 个里，**9 个是推理模型**（先推理再作答），`max_tokens` 给小了正文会是空的 ——
> 这是这条链路上最大的坑，见「七之三之三」。

> [!IMPORTANT]
> **Windows 上 `mode: 0o600` 是没用的。** Node 的 `fs.writeFileSync(..., { mode: 0o600 })`
> 在 Windows 上只会映射「只读位」，权限其实是继承自父目录的。实测 `data\refresh-state.json`
> 的 ACL 曾经是 `Authenticated Users:(I)(M)` + `Users:(I)(RX)` —— 也就是同机任何用户都能读到
> 里面的**明文** `refresh_token`、`secretAccessKey`、`securityToken`，还有 `oauth-accounts.json`
> 里自助登录的 DPoP 私钥。
>
> 现在 `src/util.mjs` 的 `writeFileSecure()` 在写完之后会额外跑一次
> `icacls <file> /inheritance:r /grant:r "<用户>:F"`，把继承关系摘掉、只授权当前用户。
> 所有落盘点（`refresh.mjs` 的 `save()`、`oauth.mjs` 的两处 `save()`）都走它。
> 顺带这个函数是**原子写**（临时文件 + fsync + rename），所以续期状态不会再出现
> 「写到一半被杀 → 文件半截 → 下次读取按空处理 → 整份状态被覆盖掉」这种数据损失。

> [!IMPORTANT]
> **改 `tools/*.ps1` 时的编码坑。** PowerShell 5.1 读**没有 BOM** 的 `.ps1` 时用的是系统
> ANSI 代码页（中文机器上是 GBK），文件里的 UTF-8 中文会被解码成乱码，严重时里面的引号会让
> 语法直接崩掉（表现为一堆 "Array index expression is missing"）。二选一：
> - 脚本**全 ASCII**（`service.ps1` / `watchdog.ps1` / `normalize-cmd.ps1` 走这条），或
> - 存成 **UTF-8 with BOM**（`screenshot.ps1` 走这条，因为它要输出中文提示）。
>

### 特性

- **SSE 透传**：上游帧原样转发（含 `reasoning_content`、`tool_calls` 增量、`usage` 尾帧），零加工
- **伪 200 错误识别**：华为网关限流时会用 HTTP 200 + `data:{"error":...}` 返回，本服务会预读首帧，
  把它还原成真正的 429 并触发重试，而不是把你的客户端搞成"空回复"
- **非流式聚合**：客户端要非流式时，仍然用上游流式接口取数（TTFB 更好），在本地拼成完整
  `chat.completion`，`tool_calls` 的 `arguments` 分片会被正确拼接
- **自动剥离不支持参数**：如 `glm-5.3` 不接受 `thinking:{"type":"disabled"}`，收到 400 后自动去参重试
- **限流冷却**：`81111/81114` 只冷却"该凭据 + 该模型"，其它模型不受影响；`APIG.1009` 冷却整条凭据
- **模型级拒绝不牵连整条凭据**：上游回 `81004`（没权限）/ `81009`（名字不认）时只给这一对组合 60 秒冷却，
  整条凭据一点都不动；池里每个号都拒过的模型会直接回 `400 model_not_available`，不再白等 3 次重试
- **凭据热重载**：桌面端刷新凭据后写回 `models.json`，本服务默认 45s 扫一次并自动替换
- **自助登录导入**：不用装也不用开 OfficeAce 桌面端，自己跑完华为 OAuth
  （PKCE + 轮询云端取授权码），点一下 → 新页面登录 → 账号自动进池并自动续期

#### 「使用倍率」这一列是什么

就是官方客户端模型列表右边那个 `0.30x` —— **用来算积分消耗的系数，越小越省**。
数据源是控制面的 `GET {网关}/v1/model-token-rates`，字段 `cost_coefficient`：

```
model                  cost_coefficient  prompt_tokens_per_point  completion_tokens_per_point
glm-5.2                0.70              4375                     1250
glm-5.1                0.67              4375                     1250
glm-5                  0.50              4375                     1250
deepseek-v3.2          0.30              4375                     1250
deepseek-v4-flash-0731 0.30              4375                     1250
deepseek-v4.1-flash    0.30              4375                     1250
```

那个接口要签名（临时 AK/SK），浏览器不能直连，所以走 `/admin/api/model-rates` 代理一发。
平时**不用额外请求**：积分刷新时已经把 `rates` 顺手带回来了（TTL 5 分钟），
点面板上的「刷新倍率」就是「现在就要看」的意思。

#### 为什么 33 个模型只有一部分有倍率

倍率表里只有**已经发布定价的基座模型**。网关的模型列表却是「全量目录 + 各种变体」
（`glm-5.2-a3`、`glm-5.2-test`、`glm-5.2-exercise`…），这些变体不单独发倍率。

所以匹配分四级，**越往后越保守**：

| 级别 | 规则 | 例子 | 显示 |
|---|---|---|---|
| ① | 精确命中 | `glm-5.2` | `0.70x` |
| ② | 紧接 `-` / `_` 分隔符 | `glm-5.2-a3` ← `glm-5.2` | `0.70x*` |
| ③ | 异体分隔符（`.` / `_` 当 `-` 用） | `glm.5.2-arkts-spark` ← `glm-5.2` | `0.70x*` |
| ④ | 我们短、表里长 | `glm-5` ← `glm-5.3-zx` | `0.70x*` |

带 `*` 的就是「借基座倍率」，悬停会说明借自谁；借不到就显示 `-`（未发布），
**不是** 0。

> **③ 判定边界时必须回原字符串看那一位。** 归一化会把 `.` 变成 `-`，于是
> `glm-5.3` 也满足「`glm-5` 后面跟 `-`」——但 `glm-5.3` 是**新一代**，
> 名字里的点是版本号不是分隔符写错，算钱未必一样。宁可留「-」，
> 也不能显示一个看起来合理但是错的数字。这条有反向对照测试兜着：
> 把判定改回看归一化串，测试必须复现出跨代误蹭。

核对脚本：

```powershell
node tools\probe-rate-match.mjs
```

它会拉真实模型 ID 逐个打印匹配结果，末尾硬校验 `glm-5.3` 系列没有被 `glm-5` 蹭走：

```
  合计：5 精确 / 11 借用 / 17 未发布  （共 33 个）
  ✓ 没有跨代误蹭（glm-5.3 系列没有被 glm-5 蹭走）
```

> 改名、停用、删除、测活、保存配置全部静默失败（服务端只能回「缺少 id」），
> 而且**整整一轮测试都没发现**，因为测试是直接打接口、绕过了这个助手。
>
> 现在 `tools/test-admin.mjs` 里有一组测试专门盯着它：把真身抠出来配假 `fetch` 跑，
> 外加一条「用旧写法必须复现 `缺少 id`」的反向对照。改完跑一遍自测。
>
> 另外记住：`admin.html` 是在**浏览器**里执行的，改完要 **Ctrl+F5 硬刷新**才生效，
> 服务端热重载不算数。

### 别名不是模型 —— 两个真踩到的坑

这两个坑都是「测试临时写了个别名，结果把别名的名字当成真模型处理」造成的，
症状完全一样：**那个名字从此消失或永久打不通，而且重启也不恢复**（因为结论落在磁盘上）。
单看表现会以为"别名功能坏了"，其实坏的是"别名被当成了模型"。

**坑一：探测把别名拉黑（`src/modelProbe.mjs`）**

探测是直接发 `POST /chat/completions` 判活的，而上游**根本不认识别名** ——
别名是我们自己在 `models.mjs` 里做的一层映射。于是探一个别名必然拿 81009，
它就被记进"打不通"，而这份名单写在 `data/model-probe.json` 里、**跨重启存活**。

后果：用户下次再起同一个别名时，它一上来就是"打不通"，哪怕指向的是个好模型。

修法：探测前用 `Object.keys(registry.alias)` 过滤掉别名。全目录都是别名时直接
`skipped`，不去打上游。

**坑二：改别名之后旧结论还在挡（`src/pool.mjs` + `src/server.mjs`）**

`rejectedModels` 是**每条凭据 × 每个模型名**的短冷却标记。「这个模型不行」
是**相对当时那份目录**得出的**结论**，不是事实。别名改了之后：

- `gpt-4o` 先指 `glm-5.3-zx`（打不通）→ 标记"不行"
- 改指 `glm-5.2`（能用的）→ 标记还在，`gpt-4o` 照样从 `/v1/models` 里消失

修法：目录变了就作废旧结论 —— `pool.clearModelRejections()`，在两个地方调：
上游目录刷新后（`ids()` 真的变了才调）、面板保存别名后。清掉之后最多让客户端
多试一次，试错会拿到准确的 400，代价可以接受。

**这两条都有降级测试**：`test-model-probe.mjs` 的【9】【10】两节是单元级，
`test-admin.mjs` 里那条「别名改指能用的模型后 gpt-4o 立刻在列表里」是端到端级
（真的改别名、真的打一发、真的看 `/v1/models`）。

排障脚本（只读，不改数据）：`node tools\diag-alias-rejection.mjs` ——
它会走一遍「无别名 → 指好的 → 指坏的 → 改回好的 → 还原」，
每一步都打印 `/v1/models` 里有没有 `gpt-4o`、`modelsUnavailable` 里有没有它。

## 七之二、号池

一个账号在磁盘上散落在三处，本服务把它们拼成一条记录（**只读不写**，不动 OfficeAce 任何文件）：

| # | 文件 | 拿到什么 |
| --- | --- | --- |
| ① | `~/.office-claw/.jiuwenclaw/config/routing_state/users/<账号ID>/models.json` | 上游网关地址 + `custom_headers.Authorization`（`Basic base64(AK:SK)`） |
| ② | `<安装目录>\packages\api\.config\secure-config-nodejs\oauth-<账号ID>.json` | 临时 AK/SK、`security_token`、**过期时间**、`project_id`、`userName`、DPoP 标记 |
| ③ | `~/.office-claw/users/<账号ID>/model.json` | 该账号可用的模型目录 |

账号 ID 就是 OfficeAce 自己的目录名：`<华为云账号ID>:<IAM用户ID>`，格式来自 `huawei-oauth.js` 的 `toPrincipal()`。

### ②是怎么读出来的

```
.oauth-profile-encryption-key   文件   → Windows DPAPI 解密 → install secret（43 字符）
oauth-<账号ID>.json             JSON   → key = sha256(install secret)
                                          alg = aes-256-gcm，iv / tag / data 都是 base64url
                                       → providerState JSON
```

所以能显示**准确的剩余时长**（临时 AK/SK 默认 24 小时，刷新令牌约 30 天），而不是靠猜。

### 号池与连接池的关系

- 号池是账号归属的**唯一权威**：某个账号被停用后，即使磁盘上 `models.json` 还在，也不会被重新捞回连接池。
- 停用 / 启用会**立刻**重算连接池（`/healthz` 的 `credentials` 会同步变化）——被测到 0 条时 `status` 变 `degraded`。
- `config.accounts.onlyEnabled`（默认 `true`）控制是否只把「已启用」账号喂给连接池。

### 手工导入

适合从别的机器搬账号：把目标机器 `models.json` 里的 `api_base` 与
`custom_headers.Authorization` 填进「导入账号 → 从别的机器搬账号」即可。导入项存在 `data/accounts.json`，
可以真正删除；本机发现的账号只能停用（删了下次扫描还会回来，面板会提示）。

> 日常加号不用填表 —— 点「导入账号」直接登录一个华为账号就行，见下一节。
> 手工导入这条路留给「搬账号」这种低频场景，所以收进了弹窗里，不占号池页的地方。

## 七之三、导入账号（自助登录）

面板上点「导入账号」，会弹出新页面让你登录一个华为账号，**登录完自己就进号池了**，不用回来点任何按钮。

![导入账号](docs/panel-import.png)

### 要加一个新号，请点「换个账号登录」

对话框里有两个按钮，区别只有一个点：**华为云那边还记不记得你**。

| 按钮 | 链接是什么 | 什么时候用 |
|---|---|---|
| **开始登录** | 直接指向授权流程 | 给**已经有的**那个号续授权（会话还在，云端直接放行，不用重填密码） |
| **换个账号登录** | 先指向华为云的**登出**，登出完再回授权流程 | **再添一个新号**（第二个、第三个……） |

为什么非得这样：

```
不带浏览器的华为云 cookie 时：
  GET /authui/v1/oauth2/authorize              → 302 /authui/login?service=…   ← 要你登录
  GET /authui/v1/oauth2/authorize&prompt=login → 同上（prompt 不影响判定）

带着 cookie 时（就是你在浏览器里已经登过华为云的状态）：
  GET /authui/v1/oauth2/authorize              → 302 直奔 redirect_uri 并带上 code
                                                 ← 也就是"直接给我登录了"，拿当前号又登一遍
```

所以「开始登录」在已经登录过的浏览器里**永远看不到登录页** —— 它只是把当前那个号重新
授权了一次。想换号只能先清会话：

```
/authui/logout?service=<authorizeUrl>
```

实测（`tools/probe-auth-switch.mjs`）这条能可靠地走到登录页：

```
  [1] 302  /authui/logout          → /authui/v1/oauth2/authorize
  [2] 302  /authui/v1/oauth2/authorize → /authui/login?service=…
  [3] 200  /authui/login           ← 停在这里，等你输账号密码
```

以后端来说就是 `POST /admin/api/login/start` 多了一个开关：

```json
{ "label": "第二个号", "forceLogin": true }
```

`forceLogin: true` 时返回的 `url` 是登出链接（`authorizeUrl` 字段仍是那个干净的授权地址，
排障时想对照就取它）。`loginFlow.view()` 会把 `forceLogin` 透传出来，面板照它决定提示文案。

> **代价要说清楚**：登出会把你**在华为云那边的登录状态一起清掉** —— 别的标签页、控制台
> 都要重新登。这是目前唯一能可靠换账号的办法（`prompt=login` 实测没效果），
> 所以面板上做成一个单独的按钮，不默认走这条。
>
> 另外：不管你用哪个按钮，登录完成后如果**授权的是号池里已有的号**，面板会明确写
> 「已**重新授权** xxx（号池里本来就有这个号）」，而不是笼统的「已添加」——
> 免得你以为加了个新号其实只是把旧的续了一遍。

### 为什么能不要桌面端

> ⚠️ 这一节曾经写着「绕开桌面端等于要自己重写整套凭据兑换，既不可靠也没必要」。
> 那个结论是**错的**，后来被推翻了。记在这里当作教训：不确定就再挖一层。

OfficeAce 走的是一条标准的 OAuth 授权码 + PKCE 流程，客户端能做，我们也能做。
每一环都是从它自己的实现里读出来的：

```
1. POST  {cloud}/v1/claw/auth/state                    →  state
     云端签发，不用任何鉴权。每次要一个新的。

2. 本地生成 PKCE（code_verifier / code_challenge）和一对 P-256 DPoP 密钥
     私钥只留本地，永远不出机器。

3. 拼 authorizeUrl，让用户去浏览器登录
     https://auth.huaweicloud.com/authui/login.html?service=<内层 OAuth2 授权>
       内层：/authui/v1/oauth2/authorize
             ?client_id=pdp5_for_agentarts
             &code_challenge=<PKCE S256>
             &state=<32 位 hex>
             &redirect_uri=https://agentarts.cn-southwest-2.myhuaweicloud.com/v1/claw/auth/callback

4. GET   {cloud}/v1/claw/auth/code?state=<state>        ← 整件事的钥匙
     202 = 用户还没登完（AgentArts.11000009）
     404 = state 不认识或过期
     200 = 拿到了 authorization code

5. POST  https://sts.cn-north-4.myhuaweicloud.com/v1/oauth2/tokens
     Content-Type: application/x-www-form-urlencoded
     DPoP: <ES256 proof JWT>
     grant_type=authorization_code & code=<code>
     & code_verifier=<verifier> & redirect_uri=<同上> & client_id=pdp5_for_agentarts
       → 临时 AK/SK + security_token + project_id + refresh_token

6. GET   {cloud}/v1/claw/client-permission-validate     （用第 5 步的凭据签名）
       → model_info.model_auth_info.model_app_key / model_app_secret
       → model_info.model_api_url_base

7. 入库：上游网关用 Basic(model_app_key:model_app_secret)，这对**不会过期**；
        临时凭据 + refresh_token + DPoP 私钥另存，用来签名控制面和自动续期。
```

**第 4 步是关键。** 云端回调页（`/v1/claw/auth/callback`）只是个终点页，
上面写着「授权成功 / 请返回客户端体验」，它**不往本机跳**。
桌面端是靠轮询 `/v1/claw/auth/code?state=` 把授权码取回来的 ——
这条从 `packages/api/dist/index.js` 里挖出来的。知道这一点，整个链路就能自己跑完。

顺带澄清一处容易误判的地方：`redirect_uri` 指向云端，看着像「必须有服务端配合」，
其实不是。PKCE 的 `code_verifier` 在请求 state 的那一方手里，云端只是暂存 code
等你去取，取的时候再验 verifier。所以**谁要的 state，谁就能取**。

### 凭据的两层，别搞混

| | 临时凭据 | 网关凭据 |
|---|---|---|
| 长什么样 | `HSTA...` 开头的 AK/SK + `security_token` | `model_app_key` / `model_app_secret` |
| 用在哪 | 签名控制面（`agentarts.*`） | 上游 MaaS 网关的 `Authorization: Basic` |
| 有效期 | **实测 2 小时**（见下） | **不过期** |
| 从哪来 | 第 5 步 | 第 6 步 |

上游干活只用网关凭据；临时凭据是拿来「问云端问题」和续期的。
所以只要第 6 步拿到过一次，这个号就能一直用到华为那边轮换密钥为止。

### 临时凭据到底活多久？过期了会怎样？

**结论：实测 2 小时，而且过期也不影响转发。**

华为云 STS 发的临时 AK/SK 本身有寿命（官方文档写"最长 24 小时"，但**实际发下来多久由服务端策略决定**，
这套 AgentArts 发的是 **2 小时**）。量一下就知道：

```powershell
node tools\probe-lifetime.mjs
```

```
  ── 逐次续期的真实寿命（以 refreshedAt / expiresAt 为准）──
  本次签发时间(本地)      到期时间(本地)        真实寿命
  2026-10-10 09:38:55   2026-10-10 11:38:55     2.00 小时
  当前这份还剩 1.96 小时（117 分钟）
  本轮寿命 2.00 小时  →  提前量 25% = 30 分钟
  →  约 87 分钟之后触发下一次自动续期
```

> **算寿命时别把时区搞混**（我第一版写错了）：日志里的 `[HH:MM:SS]` 是本机本地时间且不带日期，
> `expiresAt` 是 UTC ISO 串 —— 直接相减会凭空多出/少掉 8 小时，算出「10 小时」「-16 小时」这种值。
> 唯一可靠的锚点是 state 里的 `refreshedAt`（跟 `expiresAt` 同一套绝对时间轴）。

**时间到了会怎样？** 分两件事看，这也是最容易焦虑的地方：

| | 临时 AK/SK 过期 | 影响 |
|---|---|---|
| **转发模型**（`/v1/chat/completions`） | **完全不受影响** | 走的是不过期的网关 `Basic` 密钥 |
| 读积分 / 自动签到 | 读不出来 | 需要一份有效的临时 AK/SK 去签名 |

所以「凭据剩余时长」那个倒计时归零，**不等于号废了** —— 面板上遇到这种情况标的是
中性色的「待续期 · 转发不受影响」，不是红色「已过期」。

**过期之后怎么办？三种情形，服务自己处理前两种：**

| 情形 | 服务的行为 |
|---|---|
| ① 链子还活着（`refresh_token` 还有效，默认 30 天） | **临期前自动换一份新的**，你什么都不用做 |
| ② 链子已烧穿（所有 refresh_token 都被用过或作废） | 记一条 WARN，面板提示需要重新登录一次；此时转发依然正常 |
| ③ `refresh_token` 也过期了（30 天没开过桌面端） | 同上，点一次「导入账号」重新授权即可 |

第 ① 种是常态，由**临期自动续期任务**负责（`src/index.mjs`）：

- **提前量按比例算**，不写死小时数 —— 寿命是未知的（2 小时还是 24 小时取决于服务端策略），
  所以用「本轮寿命的 25%」（`renewLeadRatio`，上限 `renewBeforeHours` 小时）。
  2 小时寿命 → 剩 30 分钟时换；24 小时寿命 → 剩 6 小时时换。
- **检查间隔 15 分钟**，开机立刻先跑一遍（重启时凭据可能已经没剩多少，等 15 分钟就来不及了）。
- **安全阀**：只有链子还能挑出 token 时才动。挑不出就记一条
  `凭据即将过期，但续期链上挑不出可用 token，只能等重新登录` 然后不动 ——
  硬撞只会把一个必然 `STS5.1806` 的值发上去，白烧一份一次性 token。

配置项（`config.json` → `credits`）：

```json
"autoRenewCredentials": true,   // 总开关
"renewLeadRatio": 0.25,         // 提前量 = 本轮寿命 × 这个比例
"renewBeforeHours": 3           // 提前量的上限（24 小时寿命的兜底，别为"剩 6 小时"白换）
```

日志长这样：

```
[01:38:56] INFO  boot  临期自动续期已启用 {"leadRatio":0.25,"leadCapHours":3,"checkSeconds":900}
[01:38:56] INFO  boot  临期凭据已主动续期 {"id":"a1b2c3d4…","leftMinutes":108,"leadMinutes":30,
                                         "tokenSource":"rotated","expiresAt":"2026-10-10T03:38:55.877Z"}
```

> **为什么不干脆把寿命调长？** 调不了 —— 寿命是 STS 服务端定策略给的，不是我们能选的参数。
> 而且临时凭据本来就该短：它是拿来签名的，泄露窗口越小越好，出事了服务端拒绝续期就等于吊销。
> 真正该保证的是「永远有人替你提前换下一份」，那正是上面这个任务做的事。

### 用到的接口

| 接口 | 说明 |
|---|---|
| `POST /admin/api/login/start` | 要一个 state，返回 `{id, url, state, expiresInMs}` |
| `GET /admin/api/login/poll?id=` | 查进度；`status` 为 `done` 时账号已入池 |
| `POST /admin/api/login/cancel` | 取消 |
| `POST /admin/api/login/clear` | 清掉已结束的会话 |
| `GET /admin/api/login/status` | 概览：自助登录进来的账号 + 会话列表 |

`status` 取值：`pending`（等登录）→ `exchanging`（换令牌中）→ `done`
；失败分支是 `failed` / `expired` / `canceled`。

### 几个实现上的注意点

- **`state` 每次都要新的**，云端签发的，别自己编。
- **轮询是背景任务**，不靠前端驱动：服务自己每 2.5 秒问一次，
  所以关掉面板页面也不影响；服务重启也会接着轮（会话落在
  `data/login-sessions.json`，重启时自动恢复 `pending` 的）。
- **私钥不出服务端**：`/login/start` 和 `/login/poll` 的返回里只有链接和状态，
  `code_verifier`、DPoP 私钥、AK/SK 一个都不带。
- **未开通的号会明确报错**，不会干等：`client-permission-validate` 拿不到
  `model_info` 时提示「这个账号还没开通服务，需要先兑换邀请码」。
- 账号落在 `data/oauth-accounts.json`（`0600`，里面有 refresh_token 和私钥），
  元数据由 `accounts.mjs` 读进号池，所以额度查询 / 自动续期 / 连接池调度
  都当它是普通账号，没有特例分支。

### 移除一个本机账号（面板上的「删除」会不会真删掉）

分两种情况，面板和接口都按这个来：

| 账号来源 | 点「删除」的结果 |
| --- | --- |
| **手工导入**（`sources === ['imported']`） | 真删。记录在本服务的 `data/accounts.json` 里，删掉就没了 |
| **本机 OfficeAce 文件里发现的** | 记进**忽略名单**。不写 OfficeAce 的任何文件，但效果和删除一样 |

第二种为什么要这样：这类账号是从磁盘上**三处只读文件**拼出来的
（`routing_state/.../models.json`、`secure-config-nodejs/oauth-<ID>.json`、`users/<ID>/model.json`）。
抹掉内存里的记录没用 —— 下一轮 `scan()`（45 秒一轮）立刻又把它原样捡回来。
而真去删 OfficeAce 的文件就违反了本项目的硬约束，还会把桌面端弄坏。

所以做法是：把 id 记进 `data/accounts.json` 的 `ignored` 数组。之后：

- `scan()` 的建记录入口对忽略的 id 直接返回 `null`，号不会进入号池
- 它不会出现在账号列表，也不会被连接池拿去发请求
- 立刻生效，不用等下一轮扫描
- **随时能恢复**：面板「配置」页最下面有「已忽略的账号」，点「恢复」就回来了
  （默认顺带启用，因为你要把它找回来多半就是想用它）

> **这里同时修掉一个真 bug。** 老 `remove()` 里写的是：
>
> ```js
> this.meta.disabled = this.meta.disabled.filter((x) => x !== key);   // ❌
> ```
>
> 这一句是 `setEnabled()` 里「**启用**」那一半（`set.delete(key)`）照抄过来的，
> 方向反了。后果是点「删除」既不删也不停，反而会把一个**已经停用**的号
> **重新启用**，而且面板上只弹一句「已停用」让人以为成功了。
> 实测确认：点完之后 `data/accounts.json` 里 `disabled` 还是空的，
> 服务接口返回该账号 `enabled: true`。
>
> 现在的行为是「进忽略名单 + 保持停用」，并且补了回归测试盯着
> （含一条把老那一行原样搬过来跑、确认它确实会反转的对照）。
>
> 顺带一提，忽略名单里会**保留别名** —— 不然恢复页上只能看到 `a1b2c3d4`
> 这种 ID 前缀，根本认不出是哪个号。

### 还留着的老路子：走本机桌面端

面板「配置 → 授权」那一块的一键授权仍然可用，走的是本机 OfficeAce 自己的接口：

```
POST https://127.0.0.1:3004/api/login/authorize   → { authorizeUrl, state }
```

**但它要求桌面端在运行**，而且 `OFFICE_CLAW_WINDOWS_RANDOM_PORTS=true`
的时候 Windows 上端口是随机的，写死 3004 并不靠谱
（可以在 `config.auth.appApis` 里加候选地址）。
自助登录没有这些限制，是推荐路径。

> ⚠️ 一键授权这条路进来一个号之后，第一次请求进去会**自动补上网关凭据**。
> 原因见下一节。

---

## 七之三之二、两个号以上时会踩的坑（实测踩过的）

你加第二个号的时候，下面这几件**都真的发生过**，不是理论风险。

### 坑一：加了号，积分也读得到，但一个请求都转发不出去

**现象**：新号出现在账号池里、健康度写着「无凭据」、积分查得到、签到也签得上，
但连接池里只有 1 条凭据，`pool.size` 卡在 1 —— 转发永远不会选它。

**为什么**：一个号要能**转发**，需要 MaaS 网关的 `Basic base64(app_key:app_secret)`。
而反代拿这对 key 只有两个来源：

| 来源 | 谁产生的 | 有没有 |
| --- | --- | --- |
| `routing_state/users/<id>/models.json` | **桌面端**自己请求过模型时写的 | 一键授权进来的号**没有** |
| 控制面 `client-permission-validate` 的 `subscription.model_info.model_auth_info` | 自助登录那条路会顺手取回来 | 一键授权那条路**没取** |

一键授权只让桌面端写了档案和用户目录，**从来不产生 `models.json`** ——
桌面端之所以有那份文件，是因为它自己发起过对话。结果就是新号成了
"看得见、用不了"，而面板上的「今日签到 2/2」「剩余积分 13000」看着像两个号都能用。

**修法**：加了 `src/gatewayKey.mjs`，在两处补：

1. 一键授权绑定成功那一刻（`authflow.mjs` 的 `onBound`）；
2. 开机扫一遍（`index.mjs`），把历史上攒下的这种号一起修掉。

补的数据就来自控制面那个接口 —— 和自助登录走的是同一个、同一套字段，
所以**不需要用户重新登录一次**。补完自动重新发现一次，号立刻进场。

> 注意 `model_info` 在响应里的位置是 `subscription.model_info`，**不在顶层**。
> 只看顶层会误判成"这个号还没开通服务"，把一个完全正常的号报成坏的（踩过）。

想手工验一下某个号能不能补：

```powershell
node tools\probe-backfill-cred.mjs
```

它会把每个号的凭据状况打出来，并**真的用补出来的那条凭据打一发上游**。

### 坑二：随手打一个模型名，能把整个池子打哑 5 分钟

**现象**：`glm-5.3-zx` 这种"列表里有、上游没有"的模型，打一次之后
**正常模型也跟着 502**，池子里那条凭据显示 `cooldownMsLeft ≈ 268000`。

**为什么**：上游对这类请求回 **403**，而分类逻辑里 `status === 403` 直接等于
`authFailed` → `markAuthFailed()` → 整条凭据冷却 `cooldownOnAuthErrorMs`（默认 5 分钟）。
但上游那两种 403 根本不是鉴权问题：

| 上游码 | 含义 | 是谁的问题 |
| --- | --- | --- |
| `ModelArts.81004` | 这个模型你这个号没权限 | **模型** |
| `ModelArts.81009` | 这个模型名上游不认 | **模型** |
| `APIG.1009` / `AppKey or AppSecret is invalid` | 凭据真坏了 | 账号 ✅ |

**修法**：`classifyUpstream` 新增 `modelRejected`，并且 `authFailed` 明确排除它。
被拒时只给「凭据 × 模型」这个组合一个 60 秒的短冷却
（`cooldownOnModelRejectMs`），**整条凭据一点都不动**。另外：

- 别的模型完全不受影响；
- 成功过一次就**撤销**拒绝标记 —— "这个号没这个模型"是个假设，
  上游加了权限之后得能自愈；
- 池里**每条凭据都拒绝过**这个模型时，直接回一个干净的
  `400 model_not_available`，而不是把 3 次重试配额全花在一个必然失败的组合上
  （以前是重试 3 次 + 退避，白等好几秒再给你一个 502）。

### 坑三：`/v1/models` 列出来的模型，有 2/3 其实用不了

实测两个号的时候：**34 个模型里只有 11 个真的能用**，其余 23 个上游要么
`81009 Invalid model`、要么 `81004 没权限`。

**先说结论：这个问题现在被彻底修掉了，靠的是"主动探一遍"。**

早先的做法是「说真话但不解决」：`/healthz` 多一个 `modelsUnavailable`，面板上
挂一条黄色提示把名字列出来，模型本身**仍然留在 `/v1/models` 里**（理由是"客户端
配置不用改"）。这个理由站不住 —— 用户在客户端下拉框里看到 34 个模型，挨个试、
挨个 400，最后只会认为"这个反代是坏的"。**列出来就等于承诺它可用。**

修法分两步：

**① 开机主动探一遍（`src/modelProbe.mjs`）**

学习式的黑名单（"谁被打过就记下来"）在这里是**无效**的：开机时那个清单是空的，
而客户端恰恰是**开机后第一次打开下拉框那一刻**读列表的。必须提前探出来。

- 探测用 `max_tokens: 1`（被 `TINY_MAX_TOKENS` 原样透传）：只要"上游认不认这个模型"
  这一个 bit，不要它真回答。上游花 1 个 token 就回 `finish_reason: length`。
- 实测分辨 11 个能用的 / 11 个不能用的，**22/22 全对**；34 个全探一遍并发 4 只要 **16 秒**
  （串行要 88 秒，因为 `glm-5.1`/`glm-5.2` 单个就要 10~14 秒才把推理跑完）。
- 结果落盘 `data/model-probe.json`，下次开机能直接读回来（实测重启后立刻查列表就是 11 个，
  不用等 16 秒）。
- 跑在后台（`setTimeout` 15 秒后），**不阻塞启动**。
- TTL 6 小时（`probeTtlMs`），也是**打上游的额度**：号池变了只是"TTL 过了之后值得再探一次"
  的理由，不是绕过 TTL 的理由 —— 否则用户加号/删号几次就能把 34 次请求反复打出去。
- 面板可手动重探：`POST /admin/api/models/probe?force=1`。

**② 自愈：探测出来的黑名单必须能被一次真实成功撤销**

权限是活的（运营可能刚给这个号开了某个模型）。所以 `markModelUsable()` 在每次
**真正成功**的请求上会 `clear()` 掉那个模型的名字，并写盘。
⚠️ 空正文重试那条路**故意不走** `markModelUsable` —— 一次空回复只证明"凭据没坏"，
不证明"模型列得出来"。

**③ 顺带修掉一个会把它全毁掉的 bug**

`POST /admin/api/models`（面板上改别名/隐藏）以前写的是：

```js
config.models = { alias, hidden, extra };   // ← 把别的键全删了，还立刻落盘
```

于是**在面板上改一次模型设置**，就把 `hideUnavailable`、`minMaxTokens`、
`reasoningModels`、`probeOnStartup` 这些键全部抹掉并写进 `config.json`。
表现是"改了个别名，推理预算的功能就没了"，没有任何报错。
现在改成 `{ ...config.models, alias, hidden, extra }`，`test-admin.mjs` 里有反向对照
（断言 `minMaxTokens === 1024` 且 `hideUnavailable` 还在，连写两次都要成立）。

顺带把 `hideUnavailable` 补进了 `config.mjs` 的 DEFAULTS —— 它以前只写在 README 里，
代码里根本没有这个默认值（虽然读的地方用了 `!== false` 所以行为是对的，
但它在 `config.json` 里不出现，用户无从发现）。

彻底实打验证过：11 个"可用"模型逐个真发请求，**11/11 都拿到非空正文 + `finish_reason: stop`**，
探测结论与实际完全一致。

### 坑四：`/healthz` 的几个数放在一起会骗人

改之前：

```json
{"status":"ok","credentials":1,"accounts":2,"accountsEnabled":2,"creditsAccounts":"2/2","creditsRemaining":12998}
```

`credentials: 1` 是真的（只有 1 条能转发的凭据），但它和 `accounts: 2` /
`"2/2"` 摆在一起，谁都会读成"两个号都能用、额度加起来能用"。

改之后，每个数都说清自己是什么，并补了真正有区分度的字段：

```json
{
  "status": "ok",
  "credentials": 2,                  // 真正能被调度去转发的凭据条数（"能用几个号"）
  "accounts": 2,                     // 号池账号数（含没凭据、含停用）
  "accountsEnabled": 2,
  "accountsUsable": 2,               // 启用的号里健康状态为 ok 的个数 ← 关键
  "creditsAccounts": "2/2",          // 读得到积分的号 —— 不代表它们能转发
  "creditsRemaining": 12996.74,      // 所有读到额的号之和
  "creditsRemainingEnabled": 12996.74, // 只算「启用且读到额度」的号 ← 真能花的
  "modelsUnavailable": ["glm-5-test", "longcat-flash-chat-test", "glm-5.3-zx"]
}
```

`status` 的判据也改了：以前只看 `pool.size > 0`，一个号坏了照样报 `ok`；
现在要求「有凭据」**并且**「启用账号里至少有一个是健康的」。

### 坑五：假账号 ID 会永久留在盘上

桌面端授权过程中会上报一个临时 `userId`，形如 `pending-<64位hex>`。
老代码只判「真值 + 不在之前的集合里」，于是它被当成真实账号写进了
`data/accounts.json` 的 `labels`，并且**消不掉**（`setLabel` 只判 id 非空）。

**修法**（三道）：

1. `src/authflow.mjs` 的 `isRealUserId()` —— 真实 ID 是 32 位小写 hex，
   形如 `pending-…` 的直接不当新账号，等下一轮再看；
2. `src/accounts.mjs` 的 `isRealAccountId()` —— 要求 `<32hex>:<32hex>`，
   `setLabel` 和 `pruneMetaKeys()` 都用它；每次 `scan()` 顺手清一遍盘上的幽灵键；
3. `POST /admin/api/accounts/label` 对不存在的 ID 返回 **404**（以前返回 200「成功」，
   前端以为改好了）—— 那条曾经是唯一一个 HTTP 可达的活口。

`pruneMetaKeys()` 只做减法、只删**形态就不像账号**的键，所以真账号一个都不会误删 ——
哪怕 OfficeAce 没启动、一个号都扫不到，合法形态的键也原样留着。

### 坑六：签到失败的号会被每分钟重试一次，一直重试到当天结束

签到失败时**不会**标记「今天已签」（这是对的，`claimBonus` 在读凭据失败时
在写 claims 之前就 return 了），可筛选条件 `!claimedToday(id)` 于是**永远成立**，
而定时器是 60 秒一轮 —— 一个没有 AK/SK 或者没开通服务的号会被每分钟打一次。

**修法**：失败之后记 30 分钟退避再试。当天签到窗口很宽（默认 09:05 之后都算），
真要补救得回来也来得及，但不会把上游和自己按住反复打。

顺带把 **「签了」和「领到了」拆开**：上游对已领过的号回 200 + 空奖励，
代码照样记成"今天签过了"，于是面板显示「今日签到 2/2」而 `claimTotal` 是 0 ——
两个数字自相矛盾。现在 `summary` 里多一个 `claimedWithGain`，
`/healthz` 那边也不再拿这两个数凑在一起吓人。

### 坑七：一个号续期卡住，会拖住所有号

`renewPass()` 里原来是 `for + await refreshCredential` **串行**跑，而
`renewInFlight` 是个模块级**单布尔**：一个号的续期请求撞上 25 秒超时，
后面所有号的临期判断都得排队等。

**修法**：改成按账号记（`renewInFlightAccounts` 是一个 `Set`）。
同一个号不会被重复续期，但不同号之间互不阻塞。

### 坑八：汇总里的 `lastError` 是"最后一个出错账号"的

`QuotaService.lastError` 只有一个全局字段，而且**只写不清**：A 号失败过一次
留下的文案会一直被 B 号看见，B 号成功了也不会擦掉。多账号下就会出现
「两个号都 ok、各自 `error` 都是空的，汇总里却挂着一条旧错误」。

**修法**：加 `lastErrorByAccount`（按账号，成功即清除），全局那条也记上
是哪个账号留下的、该账号恢复后自动擦掉。

## 七之三之三、推理模型的 token 预算（这条链路最大的坑）

拿 `deepseek-v4.1-flash`（你口中 `deep4.1`，目录里没有叫 `deep4.1` 的名字）实测出来的。

### 症状：200 + 空正文

客户端按老习惯给 `max_tokens: 64` 问一句"说句二十个字的问候"，拿回来的是：

```json
{"choices":[{"message":{"role":"assistant","content":""},"finish_reason":"length"}],
 "usage":{"prompt_tokens":35,"completion_tokens":64,
          "completion_tokens_details":{"reasoning_tokens":64}}}
```

HTTP 200、`usage` 齐全、`reasoning_content` 里也有内容 —— 就是**正文一个字都没有**。
客户端那边看起来就是"转完圈什么都没显示"。

### 根因：上游把 `max_tokens` 当成"推理 + 正文"的总预算

直连上游（绕开本服务）实测，同一个问题：

| `max_tokens` | 正文 | `completion_tokens` | `reasoning_tokens` | `finish_reason` |
| --- | --- | --- | --- | --- |
| 1 | 空 | 1 | 1 | `length` |
| 16 | 空 | 16 | 16 | `length` |
| 64 | 空 | 64 | 64 | `length` |
| 1024 | 有 | 506 | 492 | `stop` |
| 2048 | 有 | 323 | 310 | `stop` |
| 不给 | 有 | 371 | 355 | `stop` |

推理 token 的用量在 **215 ~ 1039** 之间随机浮动。所以预算落在 1000 以下时，
有一定概率整份预算被推理吃掉、正文为空 —— 而**这是随机的**：同一问题连打 12 次，
1024 预算空 0 次，2048 反而空 1 次。**任何固定预算都会偶发踩空。**

### 而且能用的模型全是这一类

扫了目录里全部 34 个模型（`tools/probe-reasoning-models.mjs`）：

- **能用的 11 个里，9 个是推理模型**
- 名字里毫无提示的也一样：`glm-5.2` 给 `max_tokens:64`，`completion_tokens` 干到 **474**，多的一次 **8460**
- 只有 `qwen3-30b-a3b` / `qwen3-32b` 两个是真·非推理模型（`reasoning_tokens` 是 0）
- 其余 23 个当前无权限（`81004` / `81009`）

所以"按名字编一份推理模型名单"这条路是走不通的，必然漏。

### 三道防线

**① 追加推理预算**（`config.models.minMaxTokens`，默认 1024）

```
发给上游的 max_tokens = 客户端要的 + 1024
```

不是 `max(客户端要的, 1024)` —— 那样会把 `max_tokens: 1` 的正文也放开
（实测客户端要 1 个 token，拿回来 369 个）。追加式至少不改客户端的输出意图。

**`max_tokens < 16` 原样透传**（`upstream.mjs` 的 `TINY_MAX_TOKENS`）：
上游根本不按 `max_tokens` 截断正文，只要推理跑完就把整句说完。所以对
`max_tokens: 1` 这种精确请求，追加也治不了（1+1024 拿回来还是 24 个字符）。
与其越权，不如让客户端拿到它自己要求的那个结果。

| 客户端给 | 发上游 | 结果 |
| --- | --- | --- |
| 1 / 2 / 5 / 15 | 原样 | 正文空 + `length`（**这就是客户端要的"最小输出"**） |
| 16 | 1040 | 有正文 |
| 64 | 1088 | 有正文 |
| 1024 | 2048 | 有正文 |

**② 空正文自动重试一次**（非流式）

判据写得很窄，四条同时成立才重试：正文为空 **且** 没有 `tool_calls`
**且** `finish_reason === 'length'` **且** 确实产生了推理 token。
（只有 `tool_calls` 没正文是**正常**回复，不能重试。）
整个请求只重试一次，而且不占用 `maxRetries` 的配额。

**重试必须真的抬高预算** —— 这一条是后来补的，原来写错了。

第一版是**原样重发同一个 `max_tokens`**。推理开销是随机的，但预算不够的话
第二次照样不够，于是重试等于白打一遍还多花一倍时间。日志里能直接看出这件事：

```
INFO  已把过小的 max_tokens 抬到下限 {"clientAsked":64,"sentToUpstream":1088}
WARN  正文为空，重打一次 {"reasoningTokens":1080,"completionTokens":1080}
```

1088 的预算，推理吃掉 1080 —— 第二次拿的还是 1088，结果一模一样。

`tools/diag-empty-window.mjs` 把这件事量出来了（16/64/256 三档各打 12 次）：

| 重试策略 | 空正文 |
| --- | --- |
| 原样重发（错的） | **12/36**（失败的是固定的那两个问题，不是偶发） |
| 重试抬到 2048 | 10/36 |
| 重试抬到 5120 | 2/36 |
| 重试抬到 8192 | **1/48** |

现在的算法（`config.models.emptyRetryFloorTokens` / `emptyRetryContentTokens`）：

```
重试预算 = max(emptyRetryFloorTokens, 上一发的 reasoningTokens + emptyRetryContentTokens)
        = max(8192, 上一次推理用掉的 token + 0)
```

为什么用**地板**而不是"上一次的推理量 + 一点"：第二次的推理开销是**独立随机**的。
实测有第一次只烧 139 token、第二次直接烧到 10150 token 的。地板兜的就是这种情况。

为什么停在 8192 而不是继续往上：那 1/48 的失败是**病态**的 —— 观测到单发推理
能到 18904 字符（≈11800 token），要兜住这种就得给到 16384，而代价是**每次**
正常请求都可能更慢、更费额度。宁可留一个很低概率的失败，并且让那一发**看得见**：

```
WARN  重试还是被推理吃光了预算，正文依旧是空的（这一发只能这样了） {"reasoningTokens":8192,…}
```

整条路径的耗时（48 次实测）：中位 **3.3 秒**，p90 **32 秒** ——
抬高的预算是"重试那一次"才花的时间，正常请求还是走在 ① 的 1024 上。

流式走不了②（字节已经发给客户端了），但会在日志里留一条 WARN 解释原因：

```
WARN  server  流式回复正文是空的（推理把 token 用完了） {"model":"…","reasoningChars":1568,…}
```

**③ 夹住上游的硬上限**（`config.models.maxMaxTokens` / `maxMaxTokensByModel`）

这条是后来补的，因为 ① 是**加法**，而上游自己也有范围 —— 客户端给的正好是上游
上限时会被顶出去：

```
max_tokens=393216  →  393216 + 1024 = 394240  →  400 ModelArts.81001
                                                      max_tokens range is [1, 393216]
```

而且是**确定性失败**：请求不变，打一百遍一样被拒（服务已经认得出这类错误、不重试，
所以客户端看到的就是"一直报错"）。触发它的是一条很常见的链路：

```
客户端（VS Code 之类）→ 网关（按 maxOutputTokens 向客户端声明能力）
                     → 客户端照着那个数发 393216 → 到这儿被加成 394240 → 必失败
```

上游各家上限**不一样**，而且只有真打上去才知道（把客户端给的数减掉 1024，
就能用"上游实际收到的值"逐档探边界）：

| 模型 | 上限 | 上游原话 |
| --- | --- | --- |
| `glm-5.1` / `glm-5.2` / `glm-5.3` | **131072** | `max_tokens参数非法：限制数值范围[1,131072]` |
| `qwen3-32b` | **131072**（= 上下文） | `maximum context length is 131072. However, you requested 131081 tokens (9 in the messages, 131072 in the completion)` |
| `qwen3-30b-a3b` | 同上 | 同族，同一套校验 |
| `deepseek-v4.1-flash` | **393216** | `max_tokens range is [1, 393216]` |
| `kimi-k2.6` | ≥ 393216 | 打到 393216 都没拒 |

⚠️ qwen 那一行要留神：它的上限是**上下文窗口**，`max_tokens` 和提示词**一起**算，
所以配置里给 65536 是留出提示词的余量 —— 按 131072 满编，提示词一长就开始 400。

夹的是**上限**、不是下限，规则跟 ① 的"追加"正好对称：

| 客户端给 | 上限 | 发上游 | 说明 |
| --- | --- | --- | --- |
| 393216 | 393216 | 393216 | 被加法顶到 394240，夹回来（原故障用例） |
| 393216 | 131072 | 131072 | glm 那一族 |
| 1000 | 393216 | 2024 | 没到上限 → 一个字节都不动 |
| 8 | 393216 | 8 | 极小值照旧原样透传 |
| 不给 | 393216 | 不给 | 上限也不凭空造一个（上游默认够用） |

夹取会在日志里留一条，和 ① 的"抬下限"分开记（不然日志会说谎）：

```
INFO  客户端要的 max_tokens 超过上游上限，已夹到上限 {"model":"glm-5.3","clientAsked":394240,"sentToUpstream":131072}
INFO  这个模型会先推理再作答，已把过小的 max_tokens 抬到下限 {"model":"deepseek-v4.1-flash","clientAsked":1000,"sentToUpstream":2024}
```

配置（按模型族前缀命中，`glm-5` 覆盖 5.1/5.2/5.3，多个键都命中时取最长的那个；
`0` = 不夹）：

```json
"maxMaxTokens": 393216,
"maxMaxTokensByModel": { "glm-5": 131072, "qwen3": 65536 }
```

### 代价：慢

推理那 1024 个 token 是要真花时间的。`max_tokens: 64` 的短问答实测 **3 ~ 28 秒**
（`glm-5.1` 最慢 23.8s，`glm-5.2` 28.0s）。这是推理模型的本性，反代绕不开。
真嫌慢就把 `minMaxTokens` 调小赌运气，或者换 `qwen3-32b` —— 实测它 `reasoning_tokens` 是 0。

## 七之三之四、大批量压测：会话会不会断、上下文会不会丢

`tools/stress-deep41.mjs` 是一次性的"把反代往死里用"的脚本，专盯**长会话**和**高并发**
这两件在真实客户端里天天发生、但单发测试永远测不到的事。

```powershell
node tools\stress-deep41.mjs                     # 默认：24 轮 / 9000 token / 24 并发 / 60 发
node tools\stress-deep41.mjs --all               # 满规模：50 轮 / 14000 token / 48 并发 / 150 发
node tools\stress-deep41.mjs --turns=80 --burst=300 --concurrent=64   # 自己定
```

脚本只读，不改配置也不改号池；唯一副作用是**真花额度**。八节各测一件事：

| 节 | 测什么 | 怎么判 |
| --- | --- | --- |
| 1 | 连打 N 轮，看会话会不会断、上文会不会丢 | 每轮都要有非空正文；每 10 轮抽一次"第 1 轮的暗号还记不记得" |
| 2 | 长上下文：把历史撑到上万 token，在**不同深度**埋 5 个暗号 | 5 个都要找回来；`prompt_tokens` 要真的很大（证明反代没截断 messages） |
| 3 | 并发 N 发（一半流式） | 全部 200；**不能串号**（每发都带唯一编号，回答里不许出现别人的） |
| 4 | 连打几百发 | 成功率要高；后半段和前半段的中位延迟不能明显上涨（查资源泄漏） |
| 5 | 账目核对 | 号池没被打掉、没有号进冷却、`/healthz` 还 ok |
| 6 | **换号接着聊** —— 号池会轮换凭据，多轮对话跨号之后还认不认上文 | 真的发生了换号，而且第 1 轮的暗号还在 |
| 7 | 长对话里"最近的还记不记得" | 隔 80 条消息之后，最近说的 3 个暗号都要记得 |
| 8 | `/v1/models` 列出的每个模型都打一发 | 全部 200、都有正文、没有路由串台 |
| 9 | **顶到上游的硬上限**：发 5001 条消息 | 回 413 而不是 429/500；不重试；不冷却号；之后还能正常聊 |
| 10 | **多个独立会话同时聊**（每个都是多轮，各自上下文不同） | 每个都答对自己的暗号，谁都没答出别人的 |

### 实测结论（deepseek-v4.1-flash，满规模）

| 项 | 结果 |
| --- | --- |
| 50 轮连续对话 | **一次都没断**，中位延迟 995ms，第 50 轮还记得第 1 轮的暗号 |
| 13364 token 上下文 | 5 个暗号（埋在开头/22%/50%/78%/结尾）**全找回**，没截断 |
| 48 发并发 | 全部 200，**零串号**，流式 24 发全部收到 `[DONE]`、零坏帧 |
| 连打 150 发 | 成功率 **100%**，零连接失败，前半 1026ms → 后半 951ms（0.93x，无退化） |
| 跨 28 次换号 | 上文没丢 |
| 11 个模型混打 | 全部 200，都有正文 |
| 6 个会话 × 4 轮同时聊 | 各答对自己的暗号，**零串上下文** |
| 5001 条消息 | 413 + `request_too_large`，699ms 秒回，不重试、不冷却号 |

**"会话会不会断"这件事，反代这一层其实没有可断的状态** —— 它不存会话，
客户端每一轮把整份历史带过来，反代只负责原样转给上游。所以真正会"断"的只有三种：

1. **上下文被反代偷偷截断** —— 测过了，没有。`13364` 的 `prompt_tokens` 是上游报的，
   说明整份 messages 都到了上游。源码里也只有 `MAX_BODY = 64MB` 这一个上限，
   没有任何按条数或长度裁剪的地方。
2. **上游超上限** —— 那是上游回错，不是反代断的（下面那张表就是这条线在哪）。
3. **号池轮换导致"失忆"** —— 如果实现把状态挂在凭据上就会。第 6 节专门验了这一点：
   跨 28 次换号，上文还在（因为反代本来就无状态，没有挂错的地方）。

### 上游的两条上限：一条是条数，不是 token

撞墙时上游给的是 `ModelArts.81113`，原文：

```
Invalid request body, exceeds the maximum size , messages max size is: 5000.
```

**最后那句才是关键 —— `messages` 的条数上限，5000 条。跟 token 没关系。**
我第一次撞它时塞的是 7500 块 ×2 = 15000 条消息，误当成"上下文太长"了。

`tools/diag-upstream-limits.mjs` 把两条线都摸了出来（`max_tokens: 1`，
每发约 1 token，成本可以忽略）：

| 线 | 边界 | 怎么测出来的 |
| --- | --- | --- |
| `messages` **条数** | **正好 5000** | 4990 过、5000 过、**5001 拒**、5100 拒 |
| **token** 窗口 | **≥ 655713** | 逐档往上打：20523 / 41013 / 81993 / 122973 / 245913 / 409833 / **655713** 全部 200 |

也就是说：**在那台机器上根本撞不到 token 窗口**，会撞到的只有 5000 条那条线。
真实客户端很容易撞到它 —— 一段 50 轮的对话就是 100 条消息，5000 条 ≈ 2500 轮。

⚠️ 顺带一个教训：我一开始用「字符数 × 0.75」估 token，估出 60 块 ≈ 162k，
实测只有 123k —— **那段填充文本重复度极高，压缩率比自然文本好得多**。
估 token 的事只能信上游回报的 `prompt_tokens`。

### 踩到的一个真 bug：`81113` 被当成"限流"

`ModelArts.81113` 带的是 **HTTP 429**，所以它一开始落进了
`rateLimited` 那条正则（`/81111|81112|81113|81114|0308|.../`）里。后果有两层：

1. 反代拿同一个 5.5MB 的 body **原样重试满 3 遍** —— 每遍都要把 5.5MB 再传一次；
2. 错误原样透传成 **429**，客户端以为"只是暂时忙"，于是继续重试这个必然失败的请求。

但这是**确定性**失败：body 不变，打一百遍都一样大、一样被拒。修法：

| 位置 | 改动 |
| --- | --- |
| `upstream.mjs` `classifyUpstream` | 新增 `requestTooLarge`，在 `rateLimited` **之前**判；`rateLimited` 加 `!requestTooLarge` 反向条件；`retryable` 明确排除它 |
| `server.mjs` 重试循环 | `requestTooLarge` 单独一档：**直接回 413 就 `continue` 都不给**，连"记一笔失败"都不做（这不是凭据的错） |
| `server.mjs` `lastStatus` | `413` 优先于 `429`/`502` |
| `server.mjs` 收尾错误体 | `code` 给 `request_too_large`、`type` 给 `invalid_request_error`，并在 message 里补一句对策："把历史清短一些 —— 是减少消息条数，光把每条改短没用" |

反向对照也钉住了（`test-admin.mjs` 里 8 条断言）：`81111` / `81112` / `81114`
和裸 429 **仍然**按限流处理、**仍然**可重试 —— 修这条别把真限流一起误伤。

修完实测：`HTTP 413 / code=request_too_large / attempts 0 / 699ms 秒回`，
日志里只有一条 `请求超过上游上限（messages 条数太多），直接回给客户端，不再重试`，
再也没有"已尝试 3 次"。

### 记下来但不算故障的两件事

**① 上游会自己归一模型名。** 对不上的一共三类，全是正常的：

| 类 | 例子 | 谁改的 |
| --- | --- | --- |
| 别名 | `gpt-4o` → `glm-5.2` | **反代自己**（别名就该这样，`/v1/models` 里带 `alias_of`） |
| 归一大小写 | `Kimi-K2.6` → `kimi-k2.6` | 上游 |
| 归一到基座 | `deepseek-v4.1-flash-0930` → `deepseek-v4.1-flash` | 上游 |

`models.mjs` 的 `resolve()` 只在命中 `models.alias` 时替换名字、否则原样返回，
所以除别名外都是上游改的 —— **名字的最终解释权在上游**。
这跟别处踩过的「上游回 81009 说名字不认」是同一件事的两面。
脚本里因此把"回显对不上"分成三档：别名 / 上游归一（可解释）/ 真串台。

**② 云端额度计数器不能当断言用。** 它由华为那边算，本地清不掉（这点比
`usage.totals` 强 —— 那个一按「重置用量」就归零，`test-admin.mjs` 里就有一条断言
会真按一下，于是拿它做前后差值会算出 `新增成功 -39` 这种假故障）。
但它有 300 秒缓存：有时读到"跑了几百发、一分没花"，有时算出同规模的活
`14325 token/积分`、上一次却是 `7254` —— 前后两次读的快照不是同一时刻。
所以第 5 节把这一项**降级成只报数、不断言**。

## 七之三之五、给别人用之前，先把这几件事说清楚

这个项目**在自己机器上用**是稳的（见上一节的压测结论）。但要给别人用，
得先分清「能用」和「安全 / 可持续」是两回事。下面按"绕不过去"排序。

### ① 默认只听 `127.0.0.1`，别人连不上

`config.mjs` 里 `listen: { host: '127.0.0.1', port: 7864 }`。这是**故意的**：
反代本身以你的 Windows 用户身份持有所有凭据，只听回环等于"只有本机能用"。

要给别人用得改成 `0.0.0.0`（或 `OFFICEACE2API_HOST` 环境变量）。
**但改了之后，端口上的一切都暴露给能连上它的人** —— 所以下面几件事必须先做完。
启动时如果发现监听地址不是回环、而口令或 API Key 又太弱，
横幅会直接把风险打在屏幕上。

### ② 面板默认没有口令 —— 这个最要命

路由里那条校验是：

```js
if (isAdminRoute && config.admin?.token && req.headers['x-admin-token'] !== config.admin.token) {
```

注意中间那个 `config.admin?.token`：**口令为空时整个条件短路，一条都不校验。**
而 `admin.token` 的默认值就是 `''`。实测（`tools/diag-admin-auth.mjs`）：

| 配置 | `/admin` | `/admin/api/state` |
| --- | --- | --- |
| 口令为空（原默认） | 门户大开 | 门户大开，无凭据也能读约 **70KB**，含账号标签 / baseUrl / 积分 / 调用记录；写接口同样不设防 |
| 口令已设 | 401 | 401 |

现在 `config.mjs` 加了 `ensureAdminToken()`：**首次启动自动生成一个 32 位的口令**、
写回 `config.json`、并把拼好的 `?token=` 面板地址打在启动横幅里。
要退回"本机自用不校验"，把 `admin.token` 手动改回 `""` 就行。

生成用的是 `randomBytes(24)` 而不是 `Math.random()` —— 后者可预测
（V8 的 xorshift128+，看几个输出就能推后续），当密码用不合适。

### ③ 顺手修掉的：`?token=` 这条路是断的

启动横幅打的是 `${base}/admin?token=...`，401 的提示也写着
**「请在面板地址后加 ?token=你的口令」** —— 可服务端当时**只比对 `x-admin-token` 请求头**，
URL 上的 `token` 参数**根本没人读**（解析 URL 时只取了 `pathname`、把 query 丢了）。于是：

> 按提示走的人反而进不去；浏览器地址栏里老老实实带着 token，照样 401。

提示文案和实际行为不一致，比没有提示更坑。修法是两处都认：
`x-admin-token` 头（面板 JS 每条 XHR 都带）+ `?token=`（人第一次打开面板只能这么传）。

`test-admin.mjs` 里钉了四条防回归：URL 带对的能进、带错的拦住、
光有头也能进、以及**401 文案里说的用法必须真的能用** —— 防的正是
"文案和实现不一致"这一类问题。

### ④ 两套凭据互不相通，别搞混

| 面 | 路径 | 认哪个 |
| --- | --- | --- |
| OpenAI 兼容 | `/v1/*` | `apiKeys`（默认 `['sk-officeace']`） |
| 管理面板 | `/admin`、`/admin/api/*` | `admin.token` |

面板口令拿去打 `/v1` 没用，API Key 拿去打 `/admin` 也没用 —— 都实测过。
`apiKeys` 支持配多个（`OFFICEACE2API_KEYS=a,b,c`），可以按人发不同的 key。

### ⑤ 号池是**共用**的，没有按人隔离

这是设计如此，但给自己人用之前要心里有数：

* 所有调用方**共用同一批号**、同一份额度（现在是 2 个号 ≈ 1.28 万积分）。
* `usage` 只按 `apiKey` 记账，**没有配额 / 限速 / 按人封顶** —— 一个人刷爆就是大家一起没额度。
  想限制的话，现在只能给每个人发不同的 key、然后自己盯着 `usage.byApiKey`。
* `/v1/models` 的可用性、号池的轮换、模型探测结论，对所有人是同一份状态。

### ⑥ `data/` 里躺着明文长效凭据 —— 这个目录不能外发

`tools/diag-portability.mjs` 的实测结论：

| 文件 | 内容 | 形态 |
| --- | --- | --- |
| `data/oauth-accounts.json` | `refreshToken`（1238 字符的 RS256 JWT）、`authorization`（`Basic ...`）、`dpopPrivateJwk`（含私钥） | **明文** |
| `data/accounts.json` | 账号 ID / 别名 / 停用名单 | 明文（不含秘密） |

也就是说 **`data/oauth-accounts.json` ≈ 别人的号**：拿到它就能换 access_token。
另外文件 ACL 是 `BUILTIN\Users: 读` —— **这台机器上任何一个本地用户都读得到**。

好消息是 `.gitignore` 已经把 `data/*` 整个挡掉了（`git check-ignore` 验证过），
不会误提交。但"能提交"和"能拷给别人"是两件事，后者不行。

**别人要用，只有一条路：让他在自己机器上重新登录一次**（面板「换个账号登录」）。
不要拷 `data/`。

### ⑦ 依赖本机的 OfficeAce 安装

模型目录和凭据都是从本机桌面端的运行期文件里抠出来的
（`~/.office-claw/...`，以及便携安装目录下的 `.office-claw`）。
全新机器上得先装 OfficeAce、登录过一次，反代才有东西可用。

### 一句话

> **自己用：可以。给同一台机器上的自己用：可以。**
>
> **给别人用：先把 `admin.token` 设上（现在会自动生成）、把 `apiKeys` 换成别人猜不到的、
> 想清楚「号池和额度是共用的」、并且别拷 `data/` —— 让对方自己登录。**

### 顺手修掉的 4 个真问题

**① `open-panel.cmd` 打开的是裸 `/admin` → 必然 401**

加了面板口令之后，`open-panel.cmd` / `status.cmd` / `start.cmd` 里那句写死的
`http://127.0.0.1:7864/admin` 就变成了死路 —— **新用户第一次点「打开控制台」就撞 401**。
新增 `tools\admin-url.mjs`：从 `config.json` 现算端口和口令（也认 `OFFICEACE2API_PORT`），
三个脚本都改成先调它再打开。

**② 零凭据时的引导把人往死胡同里带**

原文是「请先登录并运行一次 OfficeAce 桌面端（发起一次对话），再重启本服务」。
这对着"装了桌面端、只是没登录"的人是对的，但对**根本没装 OfficeAce** 的人
（也就是只想自己加个号的人）就是死胡同：他照做也没得做。
现在启动时直接打一块提示，把「打开控制台 → 换个账号登录」摆第一位、
桌面端那条降为备选，并把带 token 的控制台地址印出来。

**③ `.cmd` 里不能写中文注释 —— 会把脚本搞崩**

这个坑得很实在。我给 `start.cmd` / `status.cmd` / `open-panel.cmd` 加了几行中文注释，
结果脚本直接跑崩：

```
'<乱码的中文注释>' is not recognized as an internal or external command
'ait' is not recognized as an internal or external command
```

原因：`cmd.exe` 是用 **OEM 代码页**（简中系统是 936/GBK）去读 `.cmd` 的，文件却存成 UTF-8。

后面的行就被当成新命令。**它不报语法错**，只报一堆莫名其妙的 `is not recognized`，
看起来像路径问题 —— 我一开始就在这条上绕了两圈。

修法：这几个 `.cmd` 一律只写**英文注释**（原文件本来就是全英文，是我改了才出的事）。
给人看的中文放进 README；`echo` 出去的中文无所谓（echo 不解析）。
`diag-fresh-clone.mjs` 第 8 节会把 9 个 `.cmd` 全查一遍非 ASCII 字节，防止再犯。

**④ 生成物别落在会被提交的目录里**

`admin-url.mjs --cmd` 会写一个中间文件给 `.cmd` 调，里面有**明文面板口令**。
第一版我写在 `tools\admin-url.vars.cmd`，`git check-ignore` 一验 —— **没被忽略**，
提交上去就是把口令连同 repo 一起发出去。改成落 `data\admin-url.vars.cmd`（`data/*` 已被挡住），
并在 `.gitignore` 里补了 `tools/*.vars.cmd` 兜一层，注释也说清"带秘密的生成物别往 tools/ 放"。

### 一个查过、已证伪的怀疑：幽灵账号

模拟时沙箱用户目录后，日志出现 `号池扫描完成 {"accounts":2,"credentials":0}` ——
**一条凭据都没有却报"2 个账号"**。当时的怀疑是：`data/accounts.json`（账号元数据，
存 ID / 别名 / 启停名单）里的键被当成了真账号，于是新用户会看到几个自己从没登录过的"幽灵账号"。

模板化地查下来**证伪了**（`tools/diag-ghost-accounts.mjs`，5/0）：

* `accounts.mjs` 里三处往 `labels` 写键的地方**全都守得很严**：
  `917` 有 `isRealAccountId()` + `this.accounts.has()` 两道门；`948` 是同一函数里
  刚 push 进 `meta.imported`、键自己造的；`996` 是 `if (acc?.label)`，`acc` 来自
  `accounts.get()`，取不到就跳过。
* 列表是遍历 `map`（真凭据 + 手工导入）生成的，`labels` 不参与生成。

（`<盘>:\软件\OfficeAce\.office-claw`、`Program Files\...`）——
这台机器装了 OfficeAce，沙箱掉 `USERPROFILE` 也躲不开那些绝对路径。
**那是我的号，不是幽灵。**

> 顺带说明一个测试上的局限：因为有这组硬编码绝对路径，在**装了 OfficeAce 的机器上
> 没法完全模拟"什么都没装"**。只能保证 `C:\Users\<用户>\.office-claw`
> （本机那两个号的真正来源）被沙箱掉。

（写这个静态检查本身也踩了两个坑：守卫检测窗口一开始只往回看 12 行，把

## 七之三之七、面板上「保存了但其实没保存」——一个被服务端宽容盖住的 bug

这个是"本机自用"这条线里唯一一个**真会影响你日常使用**的问题，
而且是典型的"UI 显示成功、数据没进去"，最难自己发现。

### 病灶：`admin.html` 的 `api()` 把真 body 覆盖了

老代码：

```js
const o = Object.assign({}, opts || {});
const hasJson = o.json !== undefined;          // ★ 传 json:true 也是 true
if (hasJson) { o.body = JSON.stringify(o.json); delete o.json; }
```

设计本意是「传 `json: {对象}` 就帮你序列化成 body」。但项目里有 **8 处**
调用写的是另一种用法：

```js
{ method: "POST", json: true, body: JSON.stringify(真实数据) }
```

这里 `json` 只当"我带了 body"的标志位。可 `hasJson` 是 `json !== undefined`，
照样为真 → 执行 `o.body = JSON.stringify(true)` → `"true"`，
**把真正的 body 覆盖成一个字符串 `"true"`**。

受影响的 8 处：

| 调用点 | 本意 |
| --- | --- |
| `/admin/api/config` ×3 | 保存 API Key、保存配置 |
| `/admin/api/models` | 保存模型别名 / 隐藏 |
| `/admin/api/refresh` ×2 | 刷新凭据 |
| `/admin/api/usage/reset` | 重置用量 |
| `/admin/api/logs/clear` | 清空日志 |
| `/admin/api/credits/refresh` | 刷新积分 |

### 为什么一直没被发现

因为**服务端是宽容的**，而且宽容得刚刚好：

```js
registry.apply({
  alias: body.alias && typeof body.alias === 'object' ? body.alias : config.models.alias,
  hidden: Array.isArray(body.hidden) ? body.hidden : config.models.hidden,
  ...
});
```

字段不是预期类型时**保留原值**、不报错、回 200。
于是：

* 后 5 个接口（refresh / usage/reset / logs/clear / credits/refresh）本来就不读
  body 字段 → 照旧工作，一点异常都没有；
* 前 2 个（保存 API Key、保存模型别名）要读字段 → 字段全缺 → 保留原值
  → **界面弹"保存成功"，实际一个字都没存**。

面板自身还有个更早的版本是"所有 POST 都发空 body"（注释里记着），
说明这一类问题在这个助手上反复出现过。

### 修法

```js
let hasBody = o.body !== undefined;
if (o.json !== undefined && o.json !== true) {   // 只有 json 是"对象"时才序列化
  o.body = JSON.stringify(o.json);
  hasBody = true;
}
delete o.json;
o.headers = Object.assign({}, H(), hasBody ? J : {}, o.headers || {});
```

两种写法都支持：`{ json: {对象} }` 和 `{ json: true, body }`。
顺手把 8 处调用点统一改成了 `{ json: {对象} }`（少一层手写 `JSON.stringify`，
也更难写错）。

### 怎么验证"面板真修好了"——不能我自己重写一遍请求

前面两次验证都白做了：

* `diag-panel-body.mjs` 里我手写 `fetch` 直接打接口 —— 那只能证明**服务端行为如何**，
  **证明不了面板修好没有**，而要验的恰恰是 `api()` 里的翻译逻辑；
* `diag-panel-alias.mjs` 同理，而且还猜错了接口形状（见下）。

正确做法：**把 `api()` 整段从 `admin.html` 里抠出来，用 `new Function` 装成真函数**
（喂真的 `fetch` / `H()` / `J()`），然后调它 —— 等价于在浏览器里点那个按钮。
`tools/diag-panel-api.mjs` 就是这么做的，并且**故意把新逻辑换回旧逻辑跑一遍做对照**：

```
【A】新版 api()：{ json: {对象} }        → ✓ 存进去了
【B】新版 api()：{ json: true, body }    → ✓ 也存进去了
【对照】老版 api()                        → ✓ 复现"静默没保存"
```

那条对照是**必须有的**：没有它，"通过"可能只是因为测试压根没测到东西
（这个项目里已经有几条断言是靠"反向对照"才发现自己是空测的）。

现在这套逻辑也进了 `tools/test-admin.mjs`（250 条断言），以后不会悄悄退化。

### 附带教训：`/admin/api/*` 上那个**误导性的 401**

诊断过程中我绕了三圈，全都栽在同一件事上：

> **未命中 `/admin/api/*` 路由的请求，会落到兜底的 API Key 检查，
> 于是"路径不存在"和"被鉴权拦住"都回 401，长得一模一样。**

具体绕法：

1. 我手写了 `/admin/api/usage`、`/admin/api/models`、`/admin/api/settings`、`/admin/api/logs`
   去探 → 4 个报 401，差点当成"面板缺 Authorization 头"去改代码。
   实际上这几个路径**根本不存在**（面板七个菜单的数据全从 `/admin/api/state` 一次拉全）。
2. 于是我从 `server.mjs` 里用正则抠出 42 条真实路由，但全用 **GET** 探 ——
   那些是 POST-only 路由，GET 不命中，照样一片 401。
3. 挑**无害的 POST**（`accounts/test`、`refresh`）实测，全 200；
   这才发现 401 是"路由没命中"的噪声，不是鉴权拦截。

破法很简单：**加一条"已知不存在"的路径作对照**。有了基线，两种 401 立刻分得清。
`diag-local-daily.mjs` 的【0】就是这条对照，别删。

顺带把真实路由的方法也钉住了（都写在 `diag-local-daily.mjs` 里）：

| 路由 | 方法 | 备注 |
| --- | --- | --- |
| `/admin/api/state` | GET | 面板主数据，七个菜单全靠它 |
| `/admin/api/auth/app` | **GET** | 第三方登录入口（POST 会落兜底变 401） |
| `/admin/api/models`、`/admin/api/config` | **POST** | 都是 POST-only，GET 探不出来 |
| `/admin/api/credits/detail` | **GET** | 参数在 query（`?id=…&force=0`） |

这个 401 的叠法也有个意外好处：随便扫 `/admin/api/xxx` 探不出路，
"这个路径存不存在"被挡住了。代价就是自己排障时别急着找 API Key。

## 七之三之八、面板日志被同一句话刷屏（「号池扫描完成」占了 68%）

### 症状：几十秒就满屏

同一句话连着出现，中间夹着授权/注册流程的 DEBUG 细节，真正要看的 WARN/ERROR
根本找不着：

```
[04:19:48] INFO accounts 号池扫描完成 {"accounts":2,"credentials":2}
[04:19:53] INFO accounts 号池扫描完成 {"accounts":2,"credentials":2}
[04:19:58] INFO accounts 号池扫描完成 {"accounts":2,"credentials":2}
```

### 根因：这句话无条件打，而调它的路径周期都很短

`accounts.scan()` 是**全量扫盘**（每个安装目录 readdir + 逐个文件读、解密），
打完还无条件记一条 INFO。调它的路径有四个，周期都不长：

| 调用方 | 周期 | 干什么 |
| --- | --- | --- |
| 一键授权的轮询（`authflow.mjs`） | **3 秒**（`auth.pollSeconds`） | 扫盘看新账号目录出现没有 |
| 注册队列（`regTimer` → 上面那条） | **5 秒**（`register.tickSeconds`） | 同上 |
| 周期刷新（`runDiscovery('interval')`） | **45 秒**（`upstream.refreshSeconds`） | 看有没有变 |
| 面板「重新扫描」按钮 | 手点 | 用户要此刻的状态 |

把 `logs/server.log` 里的时间戳抽出来统计间隔：

| 间隔 | 次数 | 是什么 |
| --- | --- | --- |
| 45 秒 | 213 | 周期刷新的正常节奏 |
| ≤ 5 秒 | 283 | 轮询方叠在一起 |
| 0 秒（同一秒里） | 118 | 两个调用方撞在一起，连扫两三遍 |

于是 400 行日志里 **274 行是同一句** —— 而这句话**没有任何信息量**：
「还是 2 个号、2 条凭据」。

### 改法：日志只认变化，扫描只认调用方

**① 有变化才 INFO**

```
有变化 → INFO   {"accounts":2,"credentials":2,"was":{"accounts":3,"credentials":3}}
没变化 → DEBUG  {"accounts":2,"credentials":2}      ← 最多每 5 分钟一条心跳
```

心跳不能省：完全静默就看不出「扫描还活着」。要确切时间看 `lastScanAt`
（`/admin/api/state` 里有）。

**② 同一秒里的重复扫描合并掉，但只对轮询方生效**

`scan({ cached: true })` 才复用上一次结果（轮询方允许「最多慢一秒」，它 3 秒后
本来就会再问一次）。**默认永远全量扫**：

| 调用 | 传参 | 为什么 |
| --- | --- | --- |
| `authflow.mjs` 的轮询 | `{ cached: true }` | 3 秒一次，慢一秒不影响收敛 |
| `runDiscovery(reason)` | `{ cached: reason === 'interval' }` | 只有周期刷新这一路能省 |
| 其余（删除/恢复/导入/面板/启动） | 默认（fresh） | 刚改完池子，必须拿此刻的真实状态 |

⚠️ 这里踩过一次：第一版是**无条件**合并，`test-admin.mjs` 里「恢复一个号 →
立刻 scan → 号必须回来」当场失败 —— `restore()` 之后紧接着的 `scan()` 拿到了
合并前的缓存。**测试是对的，代码错了**：合并必须是调用方显式要求的。

**③ 面板档位默认 INFO，而且改成 `>=` 语义**

以前是**精确匹配**（选 INFO 就只剩 INFO），于是选 INFO 会把 WARN/ERROR 一起
藏起来 —— 没人敢把默认档从「全部」挪开，而「全部」又把 DEBUG 的轮询细节
全倒出来。现在：

| 档位 | 显示 |
| --- | --- |
| 全部 | 一个不落（含 DEBUG） |
| INFO（默认） | INFO + WARN + ERROR |
| WARN | WARN + ERROR |
| ERROR | 只有 ERROR |

### 效果（同一台机器，同样的注册任务还在跑）

| 指标 | 改之前 | 改之后 |
| --- | --- | --- |
| `号池扫描完成` | 400 行里 274 行（68%），每 1~5 秒一条 | 启动打 1 条，之后没变化不打 |
| 重启后 60 秒 | 约 60 条，几乎全是同一句 | **29 条**，全是真事件（流式完成 / 凭据入池 / 续期 / 上游列表更新） |
| 面板缓冲 51 条里 | 扫描日志能占约 50 条 | **1 条** |

### 顺带发现：五条「写了但没人读」的配置

排查过程中连着撞到五条**填了不生效**的配置项。填了不生效比不写更坏 ——
它会让人以为「我调过了」，然后去别处找原因（上面那条限流事故就是这么绕远的）。

| 配置 | 怎么处理 | 真正生效的是什么 |
| --- | --- | --- |
| `auth.pollSeconds` | **接上** | 以前是 regTimer 的 5 秒 + 注册状态机 + 面板 + 桌面端四路叠加 |
| `auth.stateTtlMinutes` | **接上** | 以前代码里写死 10 分钟，改配置不生效 |
| `accounts.rescanSeconds` | **删掉** | 号池扫描听 `upstream.refreshSeconds`（45 秒）；这个键从来没有过作用 |
| `upstream.alwaysStreamUpstream` | **删掉** | 上游流式与否只看客户端：`wantStream = body.stream === true`（`server.mjs`）。这个键也没被读过 |
| `register.sms.fixedCode` | **删掉** | `sms.provider` 只实现了 `manual` / `http`，`fixed` 只活在注释里 |

删掉的三个都是**「承诺了不存在的行为」**，删掉比留着诚实 —— 真要做，
就带着代码一起回来（`alwaysStreamUpstream` 那种「上游恒流式 + 给非流式客户端
重新拼装」是个不小的功能，不是一条配置能顶的）。

### 再加一道防线：让死配置自己冒出来

一条条撞效率太低，所以补了两处自动检查：

1. **启动时**：`unknownConfigKeys()`（`config.mjs`）会挑出「配置文件里有、
   默认里没有」的项，`WARN` 一行：
   ```json
   {"keys":["upstream.alwaysStreamUpstream"],"message":"config.json 里有代码不认识的配置项（写错名字了？改了不会生效）"}
   ```
   名字写错一个字母当场就能看见。

   ⚠️ 这条告警必须放在**最前面**（紧跟 logger），不能像一开始那样写在
   `listen` 回调里 —— 单实例保护会把第二个实例挡在 `listen` 之前，
   放后面就等于「换个入口启动就看不见」。这是正对照实测出来的。

   ⚠️ 默认值是**空对象 `{}`** 的项要当**开放映射**跳过，不递归检查：
   `maxMaxTokensByModel` / `models.alias` / `upstream.extraHeaders` 这些表的键
   本来就由用户自己定。第一版没跳，于是把用户写的
   `maxMaxTokensByModel.glm-5` 报成了"不认识的配置项" —— **会喊狼来了的
   告警比没有告警更坏**：真写错名字那次就没人看了。测试里有正反两条对照
   钉住这件事。
2. **测试里**：`tools/test-admin.mjs` 的 `[配置卫生：死配置]` 一节把判据钉死 ——
   `DEFAULTS` 里**每个叶子键都必须在 `src/` 里被读到一次**（定义它的
   `config.mjs` 自己不算），外加「示例文件里不许出现默认里没有的键」。

这道防线**上线当场就抓到了东西**：`config.example.json` 里的
`credits.autoRenewCredentials` / `renewLeadRatio` / `renewBeforeHours`
在默认值里根本没有（`index.mjs` 一直在读，靠的是 `|| 0.25`、`|| 3` 这种兜底）。
补进 `DEFAULTS` 之后，三处（默认 / 示例 / 文档）才终于说的一样。
反过来说：如果没有启动时那道 `unknownConfigKeys` 告警，**这三个键会一直
在启动日志里被误报**成"代码不认识"——修一个坑顺手埋一个坑，测试正好拦住。

⚠️ 判据是"键名在源码里出现过"，属于**保守**判法：宁可漏报死配置，
也不误报让人去删一个活配置。

### 顺带踩到的坑：**服务在跑的时候别手改 config.json**

我在删这三个键的时候就踩了：

1. 服务在跑 → 我直接改盘上的 `config.json`（删掉三个键）；
2. 接着跑了一遍 `tools/test-admin.mjs`；
3. 它的「面板前端 `api()` 的 body 翻译」一节会 `POST /admin/api/models`
   试写模型别名再还原 —— 那个接口最后会 `saveConfig(config)`；
4. **`saveConfig` 写的是服务内存里那份 config**，而内存里还是老样子
   （服务只在启动时读盘），于是三个键原样回来了；
5. 重启后启动告警又把它们报了一遍 —— 看着像"删了没用"。

结论：**改 `config.json` 先停服**（`stop.cmd`），改完再起。
面板上改配置是同一条路（内存 → 盘），行为正常；只有"手改盘"和
"内存里那份"会打架。

这条也顺便解释了另一个常见困惑：**手改 `config.json` 后服务不会热加载**，
必须重启才生效（和 GCMP 那种按 mtime 热加载的行为不一样，别串了）。

## 七之三之九、一键授权：同一个 state 被四路轮询问进了限流

### 症状：注册任务失败，理由却是「授权链接超过 10 分钟未完成」

批量注册的日志：

```
WARN  register  注册任务失败 {"phone":"138****77","error":"一键授权失败：授权链接超过 10 分钟未完成，请重新发起"}
DEBUG authflow  auth flow {"state":"20d8fd…","message":"云端返回 AgentArts.1100011: Too many requests for the same state. Please retry later."}
DEBUG authflow  auth flow {"state":"20d8fd…","message":"云端返回 AgentArts.11000009: Authorization code is not ready, please retry later."}
```

看着像「用户手慢」，其实**越问越问不到**。

### 根因：一个 state 有四路调用方，而且没有节流

| 调用方 | 周期 |
| --- | --- |
| `regTimer` 轮询所有 pending 任务（`index.mjs`） | **5 秒**（`register.tickSeconds`） |
| 注册状态机自己又 `check()` 一遍 | 同上 |
| 面板「立即查询」 | 手点（自动刷新时更密） |
| 本机 OfficeAce 应用自己也在问云端 | 它自己的节奏 |

四路各打一次，云端按 state 限流，回：

```
AgentArts.1100011: Too many requests for the same state. Please retry later.
```

而旧代码只把这句话**记成一条事件**，节奏一点没变 —— 于是继续砸、继续被限流，
10 分钟到点判超时，注册任务失败。链接其实一直是好的。

### 改法：节流挂在 task 上，限流就退避

**① 每个 state 一个 `nextPollAt`**（`check(id, { force })`）

```
到点   → 问云端（同一间隔只真问一次，不管几个调用方来问）
没到点 → 不碰云端，但本机那两步（看 islogin / 扫盘）照做
```

「没到点照样做本机两步」是关键：**认「授权完成」靠的是本机那两步**，
所以就算云端这一秒被节流挡住，用户点完授权照样能立刻入池。

⚠️ 有个顺序坑：`nextPollAt` 必须**在发请求之前**就推到未来。
反过来的话，四个调用方同一瞬间进来会各发一次（它们都在 nextPollAt
被更新之前判断 due）—— 那正是要治的毛病。测试里专门有一条并发断言盯它。

**② 被限流就指数退避**

| 云端回答 | 反应 |
| --- | --- |
| `AgentArts.1100011` / HTTP 429 / 503 | 退避 ×2：10 → 20 → 40 → **60 秒封顶** |
| 正常（`11000009` / 200） | **立刻**回到 `pollSeconds` |
| 网络错误 | 按原节奏排下一次（不空转，空转就是四路一起砸） |

10 分钟有效期里退到 60 秒还有 10 次机会 —— 够把「用户刚点了授权」认出来。

**③ 「还没好」按 `error_code` 判，不许按状态码**

实测真实云端「还没好」回的是 **HTTP 202**（不是 404），而旧代码写的是
`if (r.status === 404 && error_code === '11000009')`。于是这条**正常的**回答
掉进了「其他错误」分支 —— **每一次轮询都记一条事件**，事件表只有 40 条，
几十秒就被同一句话占满，真正要看的（新增账号 / 授权完成 / 限流）全被挤掉。

**④ 注册侧：链接过期 → 换一条新的，而不是判死**

10 分钟是**给人点击**的窗口，超时是常态（人不在电脑前、注册页还没走完）。
旧代码在 `expired` 上直接 throw 成失败，于是「用户去接杯水回来」就成了一个
失败任务。现在退回 `submitted`，等 `waitBeforeAuthMs` 后重新拿一条**新链接**
（新 state，会自动出现在面板「授权任务」列表里，label 带手机号），
次数由 `maxAttempts` 兜住。

### 实测（真实云端）

| 指标 | 改之前 | 改之后 |
| --- | --- | --- |
| 30 秒里问云端几次 | 四路各打一遍（30~60 次） | **6 次**（= regTimer 的 5 秒节奏） |
| 被限流 | 反复 `1100011` | `rateLimited=0` |
| 一个任务的事件条数 | 40 条被 `not ready` 刷满 | **1 条**（只有"已申请链接"） |

### 相关测试

`tools/test-authflow-poll.mjs`（27 项）：把 `node:https` 换成假的，
**数请求次数**。这类毛病是节奏问题、不是逻辑问题，单看某一路调用方的代码
永远看不出错 —— 只有把「谁问了、问了几次、下次什么时候问」数出来才看得见。
覆盖：未到点不碰云端 / 四路并发只发一次 / 退避序列与封顶 / 恢复即回原节奏 /
429 同样退避 / 网络错误不空转 / force 只给人工 / 节流期间仍能认出授权完成 /
「还没好」不产生事件 / TTL 配置生效。

## 七之三之十、日志的另外两件事：时间用本机时区、周期发现不再刷屏

上一节说「号池扫描完成」占了 68%（七之三之八）。改完那个之后，面板上**看着还是乱** ——
这次一口气把剩下的一起收了。两个独立的问题，都在日志这条链上。

### 问题一：面板和日志文件的时间比本机慢 8 小时

**症状**：本机 13:44，面板上写着 `[05:44]`。

**根因**：`logger.mjs` 里 `ts` 用的是 `new Date().toISOString()`（UTC），而**给人看的
那一列**直接切了这个串的第 11~19 位：

```js
// 改之前
const line = `[${entry.ts.slice(11, 19)}] ...`;
```

面板 `admin.html` 也是 `l.ts.slice(11, 19)`，于是两处一起慢 8 小时。对时间的时候极容易
误判成「这是凌晨那一条」，排查反而更绕。

**修法**：`ts` **不动**（它仍是 UTC ISO —— 那是给程序和排序用的绝对时刻），只改
「给人看的那一列」：

- `logger.mjs` 导出 `localClock(d)` / `localZone(d)`，写文件和打印控制台都走 `localClock`；
- 启动时打一行 `日志时间使用本机时区 {"zone":"UTC+08:00"}`，先把「哪个区」说清楚；
- 面板加个 `hhmmss(iso)`，按**浏览器**时区换算 —— 同一份日志，换台机器看就是那台机器的
  本地时间。顺手把概览里「最近调用」表的时间也换过来了（它原来也在切 UTC）。

### 问题二：45 秒一轮的三条日志，一字不差地重复

**症状**：面板上每 45 秒冒出同样三行，真正的事件全被埋了。

**实测占比**（服务跑了 34 分钟，内存里 228 条日志）：

| 日志 | 条数 | 占比 |
| --- | --- | --- |
| `DEBUG discover discover done {"files":[三个目录名],…}` | 53 | 23% |
| `INFO boot 忽略名单拦下已删除账号的凭据 {"count":1,"reason":"interval"}` | 46 | 20% |
| `INFO boot 凭据发现完成 {"reason":"interval","credentials":2,"accounts":2,"added":0,"catalog":47}` | 46 | 20% |
| **合计** | **145** | **63%** |

**根因**：这三条都是「周期扫描」打的，而周期扫描**没有变化时说的话没有信息量**。
七之三之八 已经把 `accounts.scan()` 改成了「只在变化时说话 + 5 分钟心跳」，但发现
（discovery）这条链上的三处没跟着改。

**修法**：同一个规矩铺满三处 ——

| 日志 | 现在的规矩 |
| --- | --- |
| `discover done` | 扫到的**文件集合变了**才打（并附文件名）；没变只留 5 分钟心跳，且只报个数 |
| `忽略名单拦下…` | 拦下的那批凭据**指纹变了**才打（又删了一个号 / 恢复了一个号）；稳态闭嘴 |
| `凭据发现完成` | `reason` 不是 `interval`（说明刚发生了某件事）→ 一律 INFO；interval 但数字变了 → INFO 并带 `was`；一字没变 → 5 分钟一条 DEBUG 心跳 |

心跳不能省：没有它就看不出「这条链还活着没有」。

**改完实测**（重启后 130 秒 ≈ 3 个周期）：`discover done` **1 条**（启动那次）、
`忽略名单拦下` 1 条、`凭据发现完成` 2 条（启动 + 第一轮周期，因为 `added` 2→0
确实变了，带 `was` 说清）—— 第二批周期**一声没响** ✓。

### 顺带踩的坑：`[undefined].join(',')` 是空串，于是「第一句永远打不出来」

给「忽略名单拦下」写变化签名时，第一版是：

```js
const ignoredSig = droppedKeys.map((c) => c.key).join(',');   // ← 错
```

`discover()` 返回的凭据上**没有 `key`**（那是进连接池时才算的），所以拿到的是
`undefined`，而 `[undefined].join(',')` 在 JS 里是**空串** —— 签名恒等于「还没说过话」
的初始值 `''`，条件 `ignoredSig !== lastIgnoredSig` 永远不成立。

表现很迷惑：**重启后启动日志里那条「忽略名单拦下」直接消失**，看着像保护没生效，
实际它拦下了（当时靠 `discoverFilter` 复现确认：忽略名单集合大小 3，那条凭据
`忽略名单拦=YES`）。

修法是签名带**条数前缀**，空标识也拼不出空串：

```js
export function ignoredSignature(creds = []) {
  const ids = creds.map((c) => c?.userId || c?.accountId || c?.id || String(c?.baseUrl || '')).sort();
  return `${ids.length}|${ids.join(',')}`;
}
```

测试里专门钉了一条：`ignoredSignature([{}]) !== ''`。

**这条的教训值得单独记**：拼接签名/缓存键时，「取不到的字段」会**静默塌缩成空串**，
而空串往往正好等于「初始/未设置」状态 —— 于是代码不报错、功能却整段失效。
带个条数（或其它恒定非空的部分）前缀，这类塌缩就再也凑不出初始值了。

## 七之三之十一、工程卫生：面板轮询、子进程 stderr、两个高风险模块终于有测试了

### 一、面板每 3 秒拉一次全量 state（后台标签页也一样）

面板 `poll()` 每 3 秒 `GET /admin/api/state` 一次，然后 `renderAll()` 把当前板块的
DOM **整块重建**。这个接口的负载（实测）：

| 项 | 数值 |
| --- | --- |
| 响应体 | 约 41 KB（logs + usage + recent 三块占七成） |
| 服务端耗时 | **3.4~7 ms**（curl 连测 6 次） |
| 频率 | 每 3 秒一次 |

数字看着不大，但两件事让它值得改：一是**它跑在同一个事件循环上**，而这个循环正在
给模型请求做流式转发；二是面板的常态是「被丢在后台标签页里挂着」，那时候它一次
都不该问。

改法（`admin.html` 末尾）：`document.hidden` 时清掉定时器；`visibilitychange` 切回
前台时**立刻补一次**（不是等下一个 3 秒，否则你切回来看到的是停轮询之前的旧数据）。

> ⚠️ **这里我第一版数字量错了**，记下来免得再犯：我用 PowerShell 的
> `Invoke-WebRequest` 测到 84 ms，就把「约 85ms 的事件循环占用」写进了注释和测试名。
> 后来用 `curl -w '%{time_total}'` 复测，服务端其实只有 **3.4~7 ms** —— 那 80 多毫秒
> 大半是 **Invoke-WebRequest 自己的开销**，被我算到服务端头上了。
>
> 教训两条：① 量服务端要用不被客户端污染的尺子（`curl`，或 Node 里直接 `fetch` 计时）；
> ② 数字一旦写进注释/测试名就会跟着代码活很久，所以这次把注释和测试文案一起改成了实测值。

同一轮的清理：**41 个导出里有 8 个是真死的**。判定标准是「全仓库（src + tools +
根目录 68 个文件）与文档里，只出现在自己的定义处」——
`util.exists / homeJoin / decodeJwt / nowIso`、`logger.onLog`（连带它那个 `listeners`
集合，以及 `emit()` 里永远空转的 for 循环）、`dpapi.resetDpapiCache`、
`authflow.authLinkHints`、`discoverFilter.pickIgnoredCredentials`。
另有 33 个属于「只在本文件里用」的导出（如 `quota.bjDay` 本文件内用 6 次、外部 0 次），
那些只是导出面太宽、不影响运行，当时留着。

> 后来这批也收窄了，见下面的「七之三之十四」：判定方式从「名字有没有被提到」换成了
> 更硬的「**谁 import 了我**」，一次清掉 32 个，并加了守卫测试。

### 二、子进程的 stderr 会**绕过 logger** 漏进服务日志

写 DPAPI 测试时，测试输出里冒出一堆乱码：

```
<乱码：...Unprotect...时发生异常:...>
```

来源是 `dpapi.mjs` 起的那个 PowerShell 子进程。根因是 **`execFileSync` 在没指定
`stdio` 时，stderr 是继承父进程的** —— 子进程的报错于是直接写进服务的 stderr
（也就是 `logs\server.err.log`，那文件里确实躺着这么一行读不懂的裸文本）：
它不过 logger，没有时间戳、没有 scope，还是控制台 OEM 编码。

修法（`dpapi.mjs`）：改用 `spawnSync` + `stdio: ['ignore','pipe','pipe']`，并给
PowerShell 脚本开头加一句 `[Console]::OutputEncoding=[Text.Encoding]::UTF8`。
同样是那一次失败，现在日志里是**能读的中文**：

```
WARN dpapi DPAPI 解密失败 {"error":"DPAPI 子进程退出码 1：使用"3"个参数调用
  "Unprotect"时发生异常:"The parameter is incorrect." ...","streak":1,"giveUpForMs":0}
```

`index.mjs` 里那条「查进程创建时间」的 `execFileSync`（单实例锁要用它判断 pid 是否
被复用）也是继承 stderr 的写法，一并收窄。验证方式是看锁文件：`startMs` 仍是
`processStartMs()` 算出的非零真值（`13436521475480.2`），说明没改坏 —— 这条比
真去起第二个实例安全，因为第二个实例会先撞上 `logs\server.err.log` 被占用。

（`util.mjs` 里的 `icacls` 本来就写了 `stdio: 'ignore'`，不用动。）

### 三、两个「最容易静默出事」的模块终于有测试了

之前 262 项测试覆盖 15/23 个模块，缺口正好落在两处高风险区。现在补上。

**`tools/test-dpapi.mjs`（13 项）** —— 它是「凭据能不能读出来」的入口。实现是起子进程
解密，中间隔着 base64 编解码和一次环境变量传递，**任何一环错了都不会抛异常，
只会静默地少一个账号**。所以这里用真实的 Windows DPAPI（当前用户作用域）生成 blob
再解回来：

- 真往返（含中文）一致；同一 blob 第二次走缓存（0ms，不再起子进程）
- `OC-DPAPI-1` 文件读得出；**非该格式按明文返回，且空行会被丢掉**（这是现有语义，钉住它）
- 空文件 / 文件不存在 → `null`，不抛
- **连续 3 次坏 blob 进冷却**：之后连正确档案也不再去试（省掉注定失败的子进程），
  失败计数不再增长；但 `dpapiUnprotect` 本身不受冷却影响 —— 这两条路径的差别是
  设计的一部分（老实现是个一置就再也下不来的 `unavailable` 布尔值），一起钉住

**`tools/test-register.mjs`（25 项）** —— 批量注册的状态机，刻意**不碰网络**：

- 入队去重（同号在途不再排队）、空号丢弃、`concurrency` 收敛到 1~5
- 暂停时 `kick()` **一次都不跑**（这条坏了就会去真打上游）
- 在途任务不许删（只能删已完成/失败）；`retry()` 把失败任务退回 `pending`
- 同号在「失败/完成」之后可以重新入队（去重不能把它永久挡住）
- **`view()` 里没有验证码明文字段**，手机号只给脱敏形态 —— 面板上的东西都会进截图

## 七之三之十二、注册队列落盘、删任务那条规则、口令不再留在地址栏

这一节四件事，前三件都是「用起来才发现」的：一件是「重启就白干」，一件是
「删不掉也没人说」，一件是「口令跟着截图走」。

### 一、注册队列落盘（`data/register-tasks.json`）

队列原来是纯内存的（`this.tasks = new Map()`），重启就没了。而这条链上一个号要走
**几分钟到十几分钟**：人填图形码 → 填短信码 → 等账号在华为侧生效 → 一键授权 →
兑换邀请码。中间任何一次重启，进度全部归零、得重头再来。

设计上最要紧的一个决定：**恢复时，在途任务一律标成「失败 + 说明中断在哪一步」，
不假装还在跑。** 因为这条链的后半段靠的是**本进程内的活状态** ——
`authTaskId` 指向 AuthFlow 内存里的那条授权任务、`submittedAt` 是在等刚才那次提交、
短信码本身分钟级有效。进程一重启这些全失效了，接着跑只会卡在 `awaiting_auth` 上
反复问一条不存在的授权任务。所以恢复后的样子是：

```
状态=failed  手机号=138****00  原因=服务重启，流程中断在「待处理」（可点「重试」重来）
```

点一下「重试」就退回去重跑 —— 这比「看着像在跑其实卡死」诚实得多。

两个字段**刻意不落盘**：

| 字段 | 为什么不存 |
| --- | --- |
| `password` | 全仓库没有任何地方读它（注册是人在浏览器里完成的），存了纯白担风险 |
| `smsCode` | 分钟级有效，重启后也用不上，同样白担风险 |

手机号必须明文存（否则重启后没法接着注册），所以落盘走 `writeFileSecure`：
原子写 + `icacls` 只留当前用户，和 `data/accounts.json` 一个待遇。
另外 `HISTORY_LIMIT = 60`：在途任务永远留着，终态任务只留最近 60 条，
免得这个文件被「注册一批、清一批」慢慢养成本流水账。

**顺手踩到一个 `||` 陷阱，今天第二次**：测试里造了一条 `createdAt: 0` 的任务，
它居然躲过了历史裁剪 —— 因为 `Number(raw.createdAt) || Date.now()` 把**合法的 0
当成「缺失」**替换成「现在」，于是最老的那条排到最前面、被当成最新的留下了。
修法是只在「不是有限数」时才用默认值：

```js
function num(v, dflt = 0) {
  const n = Number(v);
  return Number.isFinite(n) ? n : dflt;
}
```

上次是 `[undefined].join(',') === ''`（忽略名单那行因此从来没打出来）。两次都是
「用默认值兜底」的写法把合法值吃掉了 —— 凡是 `a || 默认值`，先问一句
「a 合法地等于 0 / 空串 / false 的时候会发生什么」。

### 二、「只能删已完成或失败」这条规则，害了两头

`remove()` 原来的规则是只允许删终态任务，本意是护住在途任务。但它把另一种情况也
堵死了：**一条卡在「等待短信验证码」上的任务**（人不打算继续了、或者号填错了）
在面板上删不掉 —— 面板每行都渲染「删除」按钮，点下去只报错，**唯一的出路竟然是
重启服务**（重启才会把它变成「失败」，那时才删得掉）。

自测踩的是同一个坑：它跑完会删掉自己造的两个号，但删除一直失败、**而返回值没人看**，
于是**每跑一次自检就在真队列里留两条垃圾**。以前重启能把这些垃圾冲掉，队列一落盘，
它们就永久留下来了 —— 而且是「自检跑得越多、面板上越花」。

修法：允许删除任何状态的任务（删在途任务时记一条 info 日志，因为那代表「人主动放弃」），
并给删除接口补上两处断言，把静默失败堵死：

- 删除必须返回 `ok === true`（以前返回被忽略）
- **自检跑完之后，真队列必须是空的**

### 三、面板口令不再留在地址栏

地址栏里带 `?token=xxx` 有两个问题：会留在浏览器历史里，也会**出现在截图里**。
现在服务端认三处口令（`x-admin-token` 头、`?token=`、Cookie），第一次用 `?token=`
进来时顺手种一个 `o2a_admin`（HttpOnly / SameSite=Strict / 30 天），面板再用
`history.replaceState` 把地址栏抹干净（hash 保留 —— 面板靠它记住当前在哪个板块）。

为什么不用 302 重定向把 query 抹掉：**Cookie 被禁的浏览器会进死循环** ——
加 `?token=` → 302 抹掉 → 401（没有 Cookie）→ 再加 `?token=` → 又 302……
用 `replaceState` 就只是「地址栏干净了」，鉴权路径一条都没变，刷新还能靠 Cookie 进。

### 四、日志留 3 份，并给 logger 补上真跑的测试

滚动原来只留一份（`.1` 直接被覆盖）。实测吃过亏：想对「今天服务重启前后」的日志，
而那次重启刚好跨过一次滚动，**想要的那半天正好被覆盖掉** —— 排查时最需要的那段
恰恰最先被丢。现在 `.1/.2/.3`，8MB × 4 ≈ 32MB 封顶。

新增 `tools/test-logger.mjs`（9 项）。之前 logger 只有静态断言，而这个模块的失败
**全是静默的**（写日志的异常被刻意吞掉，不能让日志把服务弄挂），所以真写几轮超限
文件来钉：超过上限才滚 / 顺序没反 / 总量封顶 / 没超不滚 / 给人看的一列是本机时间
而 `entry.ts` 仍是 UTC ISO / `keepRecent` 真的裁内存 / `debug` 不落盘但进最近日志。

`test-admin` 262 → **269**（+4 口令 Cookie、+2 注册队列自清理、+1 面板轮询），

## 七之三之十三、模型名的大小写，以及「号池没变」那条捷径藏住了模型

这一节的起点是个意外：用 PowerShell 读 `data/model-probe.json` 报错 ——

```
无法转换 JSON：字典包含重复的键"Kimi-K2.6"和"kimi-k2.6"
```

**上游把同一个模型列成了两种拼法**，而我给这两种拼法各探了一次（都返回 200）。
顺着这条线查下去，挖出一个真 bug 和一个真隐患。

### 一、同一个模型，只因为大小写，一个能用、一个报错

实测（改前）：

| 请求的模型 | 结果 |
| --- | --- |
| `kimi-k2.6` | 200，正常出结果 |
| **`KIMI-K2.6`** | **404「没有这个模型：KIMI-K2.6」** |
| `不存在的模型` | 404（这条是对的） |

根子在 `checkModel()` 的判据：

```js
const known = registry.ids();
if (known.includes(registry.resolve(name))) return null;   // 精确匹配
return { status: 404, message: `没有这个模型：${name}` };
```

而 `resolve()` 只做两件事：查别名、原样透传。**上游网关本身对大小写不敏感**
（`Kimi-K2.6` 和 `kimi-k2.6` 两种拼法探测都是 200），可我们这边大小写一变就判
「模型不存在」，报的还是最容易让人怀疑上游抽风的那句话。

为什么以前没暴露：客户端一般是从 `/v1/models` 里挑名字（那儿是原样拼法），
但**手写配置**（VS Code、GCMP 的 model 字段）大小写全凭手感。

修法（`src/models.mjs`）：

* `resolve()`：别名先按精确、再按**大小写不敏感**看一遍，然后统一走 `canonical()`
  归一到清单里的那个拼法
* `ids()`：顺手做大小写去重（同一个模型只留一条，先出现的拼法为准）
* `hidden`：也按大小写不敏感匹配（配置里写小写也要能藏掉 CamelCase 那个）

两个附带好处，都是同一件事的另一面 —— **冷却、拒绝标记、探测结论是按模型名
精确记账的**：

* 归一之后，`KIMI-K2.6` 和 `kimi-k2.6` 落到同一个键上。以前一份冷却只压得住
  一种拼法，客户端换个大小写就能绕过它
* 藏模型也一样：以前 hide 掉小写拼法，客户端换成大写照样能用；现在堵上了

守住的边界：**未知名字原样返回**（不许因为"宽容"就把不存在的模型造出来），
所以拼错的模型名仍然 404 —— 这条专门有测试钉着。

验证：`KIMI-K2.6` / `kimi-k2.6` / `Kimi-k2.6` 三种写法现在都是 200；
`/v1/models` 从 11 条变 **10 条**（少掉重复的那个 Kimi）；`healthz` 的
`models` 从 28 变 **27**。新增 `tools/test-models.mjs`（14 项）钉住这一整组。

### 二、那 17 个「打不通」——我怀疑过是误判，结果是我怀疑错了

`hideUnavailable` 默认开着，所以「打不通」的模型会**从 `/v1/models` 直接消失**。
要是探测误判，用户就完全用不到那个模型了 —— 所以我先把 17 条的判据全列了出来：

| 判据 | 条数 | 含义 |
| --- | --- | --- |
| `404 ModelArts.81009` | 11 | 型号不存在 / 未开通 |
| `403 ModelArts.81004` | 4 | 该账号无此模型权限 |
| `404 ModelArts.81016` / `81010` | 2 | 同类硬拒 |

**全是上游硬拒，没有一个是超时、5xx 或 429** —— 误判的可能性排除了，
17 个确实是这两个号用不了的。顺带解释了另一个数字：`/v1/models` 的 10 条
= 11 个可用 − 1 个重复拼法。全线自洽。

（笔记里记一笔钱的事：探到可用的推理模型很贵 —— `glm-5.2` 一次探测花了
**15.7 秒**，`glm-5.1` 15.7 秒、`Kimi-K2.6` 8.0 秒；而"打不通"的那批全在
**86~332 毫秒**内被上游门口拒掉。下面第三节的成本判断就是建立在这个差别上。）

### 三、真隐患：「号池没变就沿用上次结论」会让一个模型永远回不来

探测的跳过逻辑有**两道**闸：

```js
if (Date.now() - this.lastProbeAt < ttl) return skip;                  // ① TTL 没过
if (creds === this.probedWithCredentials) return skip;                 // ② 号池没变
```

而 `creds` 是各条凭据的 `userId/index` 拼出来的串 —— **换 token、换积分都不改变它**，
所以②一旦成立就**永远**成立（①跳过后 `lastProbeAt` 不前进）。后果很实在：
上游哪天给这个账号开了 `glm-5.3-flash` 的权限，它仍然留在 `unavailable` 里，
而 `hideUnavailable` 默认开着 → 它从 `/v1/models` 消失，用户只能自己想到去点
面板上那个「重探一遍」。**"永远"比"6 小时"长得多**，这就是这条捷径的问题。

修法：号池没变时，**只复核判为「打不通」的那批**。

```
整批探测：probed: 28   seconds: 21      ← 里面有 11 次是真花钱的推理
只做复核：probed: 17   seconds:  1      ← 全是门口被拒的
```

（同一台机器、同一个号池、实机日志。判断成本时容易搞反方向：贵的恰恰是探
**可用**的那批，而"打不通"的便宜到可以随便重探。）

三条边界都钉了测试：

* 全部可用时仍然一次不打（`号池没变，也没有待复核的模型`）
* 目录里已经没有的名字不为它打上游（`prune()` 顺手丢掉旧结论）
* `force`（面板「重探一遍」）仍是**整批**探 —— 优化不许影响手动重探

还有一条是"给未来的自己省半小时"的：模型自己回来时留一行日志
（`上游后来开通了这些模型，已放回 /v1/models`）。否则用户只会看到列表在变，
却不知道为什么变。

### 四、又踩了一次同一个坑：服务在跑的时候改它的状态文件

我想验证 TTL 分支，把 `data/model-probe.json` 的 `lastProbeAt` 改老，重启一看
**还是原值** —— 因为服务**还活着**，它内存里那份在自己 `save()` 时把我改的覆盖了
（日志里读回的 `at` 是旧时间，露的馅）。当年 `config.json` 是同一种坑，笔记里
写过「改 config.json 请先 `stop.cmd`」，这次轮到 `data/` 下的运行时状态文件。

规矩统一成一句：**运行时会写回的文件（`config.json`、`data/*.json`），改之前先
`stop.cmd`**。后来按「停 → 确认 7864 端口真关了 → 改 → 起」重做，才看到那行

## 七之三之十四、导出面 = 承诺：109 → 77，并加一道守卫

上一轮（七之三之十一）扫出「33 个只在本文件里用的导出」，当时的判定方式是
**名字匹配**：某个导出名在「全仓库 + 文档」里只出现在自己的定义处，就算多余。
那时候的结论是「不影响运行，留着」—— 因为名字匹配会错杀，手工动手不放心。

这轮把判定换成 **「谁 import 了我」**，一次清掉 32 个，并且加了守卫测试。

### 一、为什么必须换判定方式：名字匹配两边都会错

三种消费者形态才算数：

```
import { x } from './y.mjs'                   ← 普通具名导入
import * as ns from './y.mjs'  →  ns.x         ← 命名空间访问
const { x } = await import('./y.mjs')          ← 动态导入解构
```

名字匹配的漏判在现场抓到 **4 个反例**，全都是「别处有个一模一样的名字，但那是别人
自己的局部定义」：

| 导出 | 在别处"被提到"的真相 | 实际情况 |
| --- | --- | --- |
| `accounts.loadOauthAccounts` | `oauth.mjs:755` 自己也有个同名局部函数 | 只有本文件用 |
| `gatewayKey.fetchGatewayKey` | `tools/probe-backfill-cred.mjs` 自己也有个同名的 | 只有本文件用 |
| `oauth.DEFAULT_REGION` | `quota.mjs:45` 自己也有一个 | **连本文件都不用**（死代码） |
| `util.shortId` | `accounts.mjs` 自己也有一个 | **连本文件都不用**（死代码） |

后两个尤其说明问题：**名字匹配会让彻底的死代码永远活着** —— 只要世界上任何地方有
个同名符号（哪怕是个测试里的局部变量 `const shortId = 'abc123'`），它就被算成"有人用"。

（另记一条：JS 正则里 `[^}]*` **跨行**，所以 `server.mjs` 那种九行的
`import { … } from './upstream.mjs'` 本来就读得到。这点最容易被怀疑成"解析器漏读"，
所以守卫里专门放了一个具名对照钉住它，见下。）

### 二、动手前的两个安全前提

* **多行 import 会不会漏解析**：先全仓库查了一遍 `import {` 的写法（单行 / 多行 /
  默认导入 / 命名空间导入），确认 `[^}]*` 覆盖多行，再确认没有 `export *` 这种
  barrel 再导出（有的话"没人 import"就不成立了），也没有 CJS 混用。
* **同批名字有没有文档依赖**：逐个人工看文档提到它们的地方 ——
  `isRealUserId` 只是被说明"逻辑在 `authflow.mjs`"，不涉及导出；`bjDay` 只是举过例子。
  所以去掉 `export` 不影响文档的任何说法。

### 三、结果：32 个、109 → 77

| 处置 | 个数 | 说明 |
| --- | --- | --- |
| 去掉 `export` 前缀 | 26 | 只有本文件自己用（含 `quota.bjDay`、`quota.fmtPoints` 这种） |
| 删掉整行 `export { … }` | 2 行 / 4 个名字 | `authflow.mjs` 的 `DEFAULT_APP_CANDIDATES / CLOUD_BASE / STATE_TTL_MS`；`discover.mjs` 的 `export { candidateRoots as _discoveryRoots }`（`candidateRoots` 留着当局部函数） |
| 连声明一起删 | 2 | `oauth.DEFAULT_REGION`、`util.shortId` —— 本文件也不用，是死代码 |

导出名总数 **109 → 77**，全仓库"导出了但没人 import"的现在剩 **0 个**。

改动方式是机械的：每处都锚定行首、要求**恰好匹配一次**，否则不改并报错（`.mjs` 里的
这些声明都带 `export` 前缀，模式唯一）。改完 11 套全绿（当时 557 项）+ 重启开机正常。

### 四、守卫：`tools/test-exports.mjs`

这类腐化是**静默**的 —— 删掉最后一个消费者时没有任何东西会提醒你。所以加一条静态
断言：`src/*.mjs` 里每个导出名，都必须能在**别的文件**（`src` 或 `tools` 都算消费者）
里找到消费者；找不到就列出违规，并提示处置（只在本文件用 → 去掉 `export`；
连本文件也不用 → 整个删掉）。

**它自己也要有对照**，否则"解析器坏了 → 解析出空集合 → 全体通过"会一直显示绿色。
所以前面有四个自检：

1. 导出名数量落在合理区间（≥ 60 且 ≤ 200）
2. 消费者索引规模（名字数 ≥ 30）
3. 一定被 import 的两个名字（`RegisterQueue`、`ModelProbe`）必须判定为「有」
4. 编造的名字必须判定为「没有」（不能一律放行）
5. 多行 import 里的名字（`quirksFor`、`TINY_MAX_TOKENS`）必须判定为「有」

项目里已有同类先例（`unknownConfigKeys()` + 死配置检测），这条是它的兄弟。
`index.mjs` 一个导出都没有（入口就是入口），所以守卫可以一刀切，不需要豁免名单。

## 七之三之十五、上游的错误装在 SSE 帧里：`code` 一直是空的

### 一、现场

`logs/server.err.log` 里躺着 64 条同一形态的告警：

```
WARN server 上游明确拒绝这个请求，不再重试
  {"model":"deepseek-v4.1-flash","code":"","message":"data:{\"error\":{\"code\":\"ModelArts.81001\",…}}"}
```

`code` 是**空串**，`message` 是**整段原始帧**。客户端收到的也是同一坨：

```
"message":"上游请求失败: data:{\"error\":{\"code\":\"ModelArts.81001\",\"message\":\"Invalid max_tokens value: -5, …\"}}"
```

### 二、根因

`classifyUpstream()` 开头只认「整段以 `{` 开头」：

```js
if (trimmed.startsWith('{')) { payload = JSON.parse(trimmed); }
```

可反代是拿 `stream: true` 打上游的（`postChat`）——**错误是装在 SSE 帧里回来的**
（`data:{"error":…}`），压根不以 `{` 开头 → 解析失败 → `code` 空、
`message` 退化成整段原文、`payload` 为 null。

### 三、后果不只是"难看"

* 客户端既看不懂，也没法按上游的错误码分支；
* `81004 / 81009`（模型没权限）、`81001`（参数不合法）、`81113`（请求体太大）那套判断，
  当时只能靠 `message` 里的原文兜着 —— 属于"碰巧还能对"；
* 日志里 `"code":""`，排查时看不到上游真正报的是什么码。

### 四、修法

新增 `parseUpstreamErrorBody()`，按「裸 JSON → **逐行剥 `data:`** → 整段里夹着一坨
JSON」的顺序找：多帧、空行、`[DONE]`、日志里那种 `^C` 前缀都能吃下；不是 JSON 时
老实返回 null（不凭空编造字段）。

同一个必然被拒的请求（`max_tokens: -5`）修复前后：

| | 客户端收到的 `message` |
| --- | --- |
| 修复前 | `上游请求失败: data:{\"error\":{\"code\":\"ModelArts.81001\",…}}` |
| 修复后 | `上游请求失败: InvalidParamException: request param validation error, Invalid max_tokens value: -5, max_tokens must be between 0 and 131072.` |

服务端日志那行也从 `"code":""` 变成 `"code":"ModelArts.81001"`。

### 五、测试

`tools/test-admin.mjs` 新增一节「上游分类：错误体是 SSE 帧时也要能解析」**8 项**：
SSE 帧的 code/message/payload、`81001 → badRequest`、多帧 + `[DONE]` 的
`81004 → modelRejected`、带 `^C` 前缀的 `81113 → requestTooLarge`、非 JSON 老实回退、
裸 JSON（非流式）那条路径行为不变。

### 顺带：`logs/server.err.log` 只涨不滚

`server.log` 由 logger 自己滚（8 MB × 3 代），但 `err.log` 是 `run-bg.cmd` 里 `2>>`
的**重定向目标**，没人替它滚。它的定位本来就是"node 在日志系统起来之前就死了"的兜底，
那就该有界 —— 于是在 `run-bg.cmd` 里、**node 启动之前**加了一段滚动
（起进程之后再改名会撞上 Windows 的文件句柄共享冲突）。

实测：灌到 31.4 MB → 启动后 `server.err.log` 归零、`server.err.log.1` = 32,187 KB ✓；
文件只有 0 KB 时再启动一次，一份都不动 ✓。阈值 8 MB / 3 代与 `logger.mjs` 对齐
（cmd 里没法 import JS 常量，只能写死并注明出处）。

## 七之四、批量注册

### 真实边界，先说清楚

华为云注册页（`https://reg.huaweicloud.com/registerui/register.html`）必须过
**图形验证码 + 短信验证码**。图形验证码由服务端下发、一次性，没有稳定可复用的自动化通道。
所以本模块把它做成「队列 + 状态机 + 可插拔接码」：

| 环节 | 自动化 |
| --- | --- |
| 生成带手机号的注册链接 | ✅ 自动 |
| 取短信验证码 | ✅ 可插拔（手工 / 接码平台 / 固定码） |
| 检测账号生效 | ✅ 自动（扫号池） |
| 一键授权 | ✅ 自动（走上一节链路） |
| 用别名并入号池 | ✅ 自动 |
| 兑换邀请码开通额度 | ✅ 自动（`/api/login/invitation`） |
| 填图形验证码、点提交 | ❌ 人工，两步 |

### 短信验证码来源

```jsonc
"register": {
  "sms": {
    "provider": "manual",          // manual | http
    "http": {
      "urlTemplate": "https://sms.example.com/api/get?phone={phone}&project={project}",
      "project": "",
      "method": "GET",
      "codePath": "data.code",     // 从响应 JSON 里取码的点分路径
      "headers": {},
      "timeoutMs": 20000
    }
  }
}
```

- `manual` —— 面板任务行里直接填码（最省事，一个号填一次）
- `http` —— 接码平台，`{phone}` / `{project}` 会被替换；取不到码会自动退回手工填
- `fixed` —— 固定码，本地联调 / 自建环境用

### 状态机

```
pending → opening → needcode → submitted → awaiting_auth → activating → done
                                                                    ↘ failed
```

每个任务保留最近 30 条事件，失败可重试（`maxAttempts` 默认 3），并发默认 1（`register.concurrency`）。

## 七之五、积分额度（每个号还剩多少）

面板侧边栏「**积分额度**」页，以及「号池」页顶部的积分总览，会告诉你**每个账号还能跑多少**。

### 一句话看懂

```
【个人体验版】正常，有效期还剩 32 天
到期：2026/11/9 00:43:17

总共 6500 积分   已用 18.83   剩余 6481.17
  套餐积分 500 / 500
  奖励积分 5981.17 / 6000
  联网搜索剩 200 次（共 200）

奖励明细：
  新用户专属福利  剩 4000 / 4000      到 2026/11/8 16:43:19
  每日签到有礼    剩 987.13 / 1000    到 2026/10/8 23:59:59
  国庆黄金周·登录翻倍礼  剩 994.04 / 1000  到 2026/10/8 23:59:59
```

### 积分是什么单位

额度单位叫 **`officeace_points`（积分）**，不是 token。模型按积分扣费，换算率由官方 `/v1/model-token-rates` 给出：

| 模型 | 输入 token / 积分 | 输出 token / 积分 | 缓存 token / 积分 | 成本系数 |
| --- | --- | --- | --- | --- |
| `glm-5.2` | 4375 | 1250 | 17500 | 0.70 |
| `glm-5.1` | 4375 | 1250 | 17500 | 0.67 |
| `glm-5` | 4375 | 1250 | 17500 | 0.50 |
| `deepseek-v3.2` | 4375 | 1250 | 17500 | 0.30 |
| `deepseek-v4-flash-0731` | 4375 | 1250 | 17500 | 0.30 |
| `deepseek-v4.1-flash` | 4375 | 1250 | 17500 | 0.30 |

也就是说跑 `deepseek-v3.2` 时 **1 积分 ≈ 4375 输入 token**，缓存命中时 1 积分能换 17500 token（最划算）。
`cost_coefficient` 是相对倍率，数值越小越便宜。

### 怎么算出来的

**额度不在本机**，由华为云持有。本服务直接用账号的临时 AK/SK 去问，**本机 OfficeAce 登录与否不影响**——
凭据过期还会自动用 `refresh_token` 换新的（见 [七之六](#七之六自动续期--每日签到--服务守护)）：

| # | 请求 | 拿到什么 |
| --- | --- | --- |
| ① | `GET {agentarts}/v1/claw/client-permission-validate` | 校验凭据；返回该账号的专属网关 `model_api_url_base` |
| ② | `GET {网关}/v1/subscription`（头 `x-subscription-type: v2`） | 套餐 + 积分总额 + 已用 + 奖励明细 |
| ③ | `GET {网关}/v1/subscription/usage?sku_attr_code=officeace_points&aggregation=day` | 每天花了多少积分 / 多少 token |
| ④ | `GET {网关}/v1/model-token-rates` | 上面那张费率表 |

② 的响应结构（截取关键字段）：

```jsonc
{
  "subscribe_status": "SUBSCRIBED",
  "skus": [{
    "sku_code": "officeace.personal.package.trial",
    "sku_name": "个人体验版",
    "expired_time": "2026-11-08T16:43:17.412Z",
    "quotas": [
      { "sku_attr_code": "online_search_count", "sku_value": "200", "current_value": "0" },
      { "sku_attr_code": "officeace_points",     "sku_value": "500", "current_value": "0" }
    ]
  }],
  "bonus_skus": [
    { "activity_name": "新用户专属福利", "points": "4000", "current_value": "0" }
  ],
  "model_infos": [{ "model_api_url_base": "modelgw-0004.officeace.cn-southwest-2.huaweicloud-agentarts.com" }]
}
```

计算规则（和 OfficeAce 前端口径完全一致）：

```
剩余积分 = Σ sku_value − Σ current_value        // 只看未过期的 quotas，sku_attr_code = officeace_points
奖励剩余 = Σ points    − Σ current_value        // expired_time 已过的奖励不计入
总剩余   = 套餐剩余 + 奖励剩余
```

> **扣费顺序**：先到期早的先用 —— 也就是先扣奖励，再扣套餐。所以看到「套餐 500 一分没动、奖励掉了 18.83」是正常的。

### 认证：华为 V11-HMAC-SHA256

`/v1/claw/*` 用标准的 `SDK-HMAC-SHA256`；但**模型网关 `/v1/subscription*` 只认 `V11-HMAC-SHA256`**
（用错会回 `APIG.0624 Unsupported signature algorithm`）。V11 多了一层区域作用域，签名密钥要先派生：

```
CredentialScope = <YYYYMMDD>/<region>/apic                    // region = cn-southwest-2
sdkDate         = 20261008T094600Z                            // ISO 去掉 - : 和毫秒
CanonicalURI    = 路径分段逐个 rfc3986，末尾补 /
CanonicalQuery  = 按 key→value 排序，k=v 用 & 连接
CanonicalReq    = [方法, URI, Query, "头1:v1\n头2:v2\n", "头1;头2", sha256(体)].join("\n")
StringToSign    = ["V11-HMAC-SHA256", sdkDate, scope, sha256(CanonicalReq)].join("\n")

SigningKey = HMAC(HMAC(AK, SK), scope + 0x01)[0..32]          // 取前 32 字节，再转 hex 当密钥
Signature  = hex(HMAC(SigningKey, StringToSign))

Authorization: V11-HMAC-SHA256 Credential=<AK>/<scope>, SignedHeaders=<小写头名;分号连接>, Signature=<sig>
```

参与签名的头：`x-sdk-date`、`x-security-token`、`host`、`x-project-id`，以及自定义头（如 `x-subscription-type`）。
GET 请求**不带** `Content-Type`。这些细节都能在 `src/quota.mjs` 里看到完整实现。

### 省额度的几个玩法

- **看「按此速度还能用多久」**：面板会按近 7 天的日均消耗外推，直接告诉你还能撑多少天。
- **优先用便宜的模型**：`deepseek-v4.1-flash` / `deepseek-v3.2` 系数只有 `0.30`，是 `glm-5.2` 的 43%。
- **让缓存命中**：`cached_tokens_per_point` 是 `prompt_tokens_per_point` 的 4 倍，多轮对话里保持前缀稳定最省。
- **停用号不影响额度查询**：停用只影响它是否被喂给连接池，积分照常能看，方便留作备用号。
- **每天签一次到**：白送的 1000 积分，一天不领就作废 → 见下一节。

> 查询额度全程**只读**，不会消耗任何积分，也不会改动 OfficeAce 或华为云上的任何数据。
> 只有两处会写：`data/refresh-state.json`（轮换后的 refresh_token）和 `data/bonus-claims.json`（签到记录）。
> OfficeAce 自己的文件始终只读。

## 七之六、自动续期 · 每日签到 · 服务守护

这一节解决三个「放着自己就会坏」的问题。

### 问题一：临时 AK/SK 只有 24 小时

OfficeAce 给的是**临时凭据**（`sts` 发的，寿命 24 小时）。过期之后额度查询、上游调用全部 401，
以前只能重新登录一次 OfficeAce —— 每天一次，很烦。

**现在会自动续期。** 同一份档案里的 `refresh_token` 有 **30 天**寿命，拿它去 IAM 换新 AK/SK 即可：

```
POST https://sts.cn-north-4.myhuaweicloud.com/v1/oauth2/tokens
Content-Type: application/x-www-form-urlencoded
DPoP: <ES256 签名的 DPoP proof JWT>

client_id=pdp5_for_agentarts
grant_type=refresh_token
refresh_token=<档案里的 refresh_token>

→ { credentials: { access_key_id, secret_access_key, security_token, expiration, project_id },
    refresh_token: <轮换后的新 token>, id_token: ... }
```

DPoP proof 的结构（纯 Node 内置 `crypto` 实现，不引依赖）：

```jsonc
// header（只带公钥，绝不能带私钥）
{ "typ": "dpop+jwt", "alg": "ES256", "jwk": { "kty": "EC", "x": "...", "y": "...", "crv": "P-256" } }
// payload
{ "htm": "POST", "htu": "<tokenUrl>", "iat": 1791507599, "jti": "<16 字节随机 hex>" }
// 签名：ECDSA-P256-SHA256，raw R||S 共 64 字节，base64url
```

**坑（已经踩过）：`refresh_token` 是一次性轮换的。** 换回来的新 token 才是下次能用的，
旧的重放会得到 `STS5.1806 the refresh token has been used`。

而 OfficeAce 磁盘上那份档案是**只读**的，它的 token 永远是初始的 `T0`，不会更新。
所以本服务自己记住「磁盘那份动过没有」：

| 记录状态 | 判断 | 用哪个 |
| --- | --- | --- |
| `diskTokenUsed` 为空 | 从没用过磁盘那份 | 用磁盘的 `T0` |
| `diskTokenUsed` 等于磁盘那份 | 磁盘是旧的 | 用轮换出来的 `Tn` |
| `diskTokenUsed` 不等于磁盘那份 | App 自己重新登录、写了份新的 | 跟磁盘走 |
| 两边都被拉黑 | 链子彻底断了 | 不发请求，直接提示需要重新登录 |

> **`diskTokenUsed` 只跟「档案那条线」走，绝不能被轮换值带偏。**
> 这条不变式是整条链不打架的关键。判断「这次发的是不是档案那条线的那一份」
> 交给调用方（`record` 的 `sentDiskToken`，取 `pick.source` 是否 `disk*`），
> **不要**用字符串相等去猜 —— 发出去的 token 跟档案上那份相等，恰恰说明它就是
> 档案那条线的。一旦让它指向轮换值，就会出现两种坏结果：
>
> - 下一轮看到「档案 == 锚点」，放着新鲜 token 不用，去捡一个刚被拒过的；
> - 或者反过来误判「档案被换新了」，每次续期都触发一次多余的「重新上膛」，
>   **每上膛一次白烧一份一次性 `refresh_token`**（实测日志里 90 秒连烧 5 次）。
>
> 另外两个字段的分工也要分清：
>
> | 字段 | 含义 | 来源 |
> | --- | --- | --- |
> | `deadTokens` | **服务器明确拒过**（`STS5.1806`），再发必拒 | `breakChain()` |
> | `consumed` | 我们发过、**服务器认了**（200）的单次性 token | `record()` |
>
> `pickToken` 两个都要排除。但「服务器把同一份 token 原样回给我们」这种情况
> 两样都不算 —— 那是服务器自己说它还能用，把它当死值就等于自己把链子掐了。

> **这里踩过一个很深的坑，值得记下来。**
>
> 最初的实现是用一个数组存「我们消费过的 token 链」，再靠它反推磁盘那份是不是旧的。
> 问题出在那个数组有 `.slice(-12)` 的上限：**第 14 次续期**时，磁盘锚点 `T0`
> 被挤出窗口，于是判断逻辑走进「磁盘不在链里 → 跟磁盘走」的分支，
> 把早已作废的 `T0` 当成新 token 发上去 → `STS5.1806`。
> 而当时的失败处理更糟：它把 `lastUsedToken`、`rotatedToken`、`consumed` 全删了，
> 其中 `rotatedToken` 恰恰是当时**唯一还可能有效**的东西。删完下一轮又退回 `T0`
> （正是刚被拒的那个），于是永久卡死，重启也好不了。
>
> 凭据寿命实测只有 2 小时，所以这个坑**一天之内必然踩到**。
>
> 现在改成两个显式值：`diskTokenUsed`（一个字符串，不是会溢出的数组）
> 和 `deadTokens`（确认作废的 token）。判断不再依赖任何有上限的结构。
> `breakChain()` 也只拉黑被拒的那一份 —— 轮换值被拒才清轮换值。
>
> **回归测试**：`tools/test-refresh-chain.mjs` 用一个「用掉即作废」的假 STS
> 连跑 30 次续期，断言一次都不能失败；文件末尾还把老逻辑原样搬过来跑一遍做对照，
> 确认它确实会在第 14 次断（不然这个测试就是空测）。
>
> 老格式的 `refresh-state.json` 会在启动时自动迁移（`_migrate()`），不用手工处理。

轮换结果存在 `data/refresh-state.json`。**OfficeAce 自己的文件不动**，
所以 App 那边不受影响；万一 App 也重新登录换了 token，上面那张表会自动切回去。

#### 链子烧穿之后要能自愈（rearm）

`refresh_token` 是一次性的。桌面端和我们各转各的，只要撞一次 `STS5.1806`，
手里能用的 token 就都没了 —— `pickToken` 会返回 `source: 'none'`，从此这个号
只能重新登录。而「重新登录」本来就会发一份**全新的** `refresh_token` 下来
（自助登录、桌面端重登都算）。所以这里补了一条自愈路径：

```text
rearm(accountId, 新 token)      ← 用新一轮登录发下来的 token 重新上膛
```

两个容易写错的点，都实测踩过：

| 踩的坑 | 现象 | 正确做法 |
| --- | --- | --- |
| 把**新 token**写进 `diskTokenUsed` | 上膛了却仍然报「token 都作废了」 | 那个字段的语义是「磁盘那份**已经被消费掉**了」。锚点必须仍然指向**上一轮消费掉的那份**，新 token 不在死名单里、又跟锚点不一样 → 走动 `pickToken` 的 `disk-renewed` 分支 |
| 上膛时 `target.profile = {...}` 换了新对象 | 「刚上膛完又报 token 全废」 | 必须**原地改** `profile.refreshToken`。调用方手里攥着的是同一个引用，换成新对象等于白上膛 |
| 续期成功后不回写轮换出来的 token | **第二轮**就原地判 `none`，一次成功后立刻断 | 续期成功要把 `refresh-state.rotatedToken` 回填到档案上（同样只改内存）。不回写的话下一轮拿老锚点去问，必然判「磁盘那份早用过」 |
| 「该不该上膛」只看 token 字面是否相等 | 明明还能用也去上膛一次，把链子弄断 | 权威判据是 `pickToken` 会不会判 `none`（`_chainWouldPickNone`），跟 `CredentialRefresher` 内部问的是同一个问题 |

另外 `record()`（每轮成功续期都调）以前是**逐次重建**整条记录的，会把 `rearm`
留下的 `broken` 标记在第一次成功之后抹掉 —— 表现是「刚自愈完，面板又显示已断链」。
现在带 `...prev`，并且成功续期本身就会把 `broken` 收掉。

> **回归测试**：`tools/test-rearm-chain.mjs`（23 项）用假 STS 把
> 「烧穿 → 上膛 → 第一轮 → 第二轮 → 第三轮 → 再烧穿 → 再上膛」整条路径跑一遍，
> 专门断言「第二轮**不需要**再上膛、且用的是轮换那份」和「回写之后 `pickToken` 不再判 `none`」——
> 这两条就是上面那两个坑的探针。

`data/refresh-state.json` 里的 `broken` / `brokenReason` 只用来给面板标红，
**不参与**「该用哪份 token」的判断；链子真断了靠 `pickToken` 返回 `none` 说话。

#### 续期后要回填，否则面板会一直喊「已过期」

续期成功了，但**磁盘档案里的 `expiresAt` 还是昨天那个**——OfficeAce 不会去更新它。
结果是：请求跑得好好的，账号列表却红着一行「已过期」，`已过期` 统计也是 1 而不是 0，
看着像坏了。因为面板读的是磁盘档案，而真正在用的是内存里换回来的那套。

解决办法：续期成功时把新凭据**回填进内存里的账号档案**（`AccountStore.applyRefreshedCredential`），
所有消费者——列表、统计、健康度、连接池——自动看到新值。三条保证：

- **只改内存**，`acc.profile` 上的 `refreshToken` 一个字都不碰（碰了轮换链就断了）
- 磁盘原始过期时间留在 `diskExpiresAt` 上，面板可以对比着显示「档案那份已过期」
- `scan()` 之后会自动重新盖上，所以磁盘上那份过期的旧凭据不会把显示带偏

**重启也要对。** 内存里的 `refreshed` 映射一重启就空了，所以启动时会读一遍
`data/refresh-state.json`，把里面**还没过期**的凭据回灌回去（`RefreshState.list()`）。
不回灌的话，重启后到下一次续期之间，面板会短暂显示成「已过期」。

健康度也因此多了一个状态词：续期来的凭据显示 **「已自动续期 · 凭据剩 N 小时」**，
而不是笼统的「有效」，一眼能看出这个号是原装凭据还是我们换过的。

> 顺手修掉的边界：如果一个**已经过期**的凭据被回填进来，它会把手头那条还能用的从映射里挤掉，
> 下次 `scan()` 就没东西可套、档案又退回磁盘上的旧值。现在过期凭据直接挡在门外。

### 问题二：签到积分当天不领就没了

「每日签到有礼」「登录翻倍礼」这类活动值 **1000 积分**，但 `expired_time` 是**当天 23:59:59**——
一天不领就作废。面板上有「一键签到」，也会每天定时自动领。

```
POST {网关}/v1/subscription/bonus/claim
Content-Type: application/json;charset=utf8
{}
```

**坑（也踩过）：body 不能省。** 官方的调用点是「无 body 的 POST」，但实测那样会返回
`500 OfficeAce.11020001 内部服务器错误`；**必须带上 `Content-Type: application/json` 且 body 给个 `{}`**
才返回 200。所以这里跟官方写法**故意不一样**。

返回的 `bonus_skus` 就是当前所有奖励活动。同一天重复领不会报错，只是列表不变，
所以本服务自己记 `data/bonus-claims.json`，当天签过就跳过。

实测一次：

```
签到前：新用户专属福利 4000  ·  套餐 500                    → 剩 4500
签到后：新用户专属福利 4000  ·  每日签到有礼 1000
                            ·  国庆黄金周·登录翻倍礼 1000
                            ·  套餐 500                    → 剩 6500   ✅ +2000
```

### 问题三：服务半夜会自己死掉

现象：日志停在某个时刻，端口不通，计划任务状态是 `Ready` 而不是 `Running`。
原因是 Task Scheduler 自带的 `RestartOnFailure` **只在任务以非零码退出时才触发**——
进程被误杀、或者崩溃后由处理器正常 `exit(0)`，在计划任务眼里都算「成功」，于是永远不会被拉起。

**现在计划任务的载荷是 `tools/watchdog.ps1`**，不是 `node.exe`：

```
[2026-10-09 09:11:44] watchdog up: node=D:\软件\OfficeAce\tools\node\node.exe pid=20292
[2026-10-09 09:11:46] starting server
[2026-10-09 09:12:02] server exited code= after 17s      ← 这里是我们强杀它做测试
[2026-10-09 09:12:02] restarting in 3s (fast-exit streak 1)
[2026-10-09 09:12:06] starting server                     ← 4 秒后自愈
```

守护做的事：

- 无限循环拉起服务，**不管退出码是什么**；
- 起之前先看端口上的实例**是不是还活着**（`/admin/api/state` 能通就不动它）；
  只有真死了才清掉，免得两个守护互相杀对方的服务；
- **单实例锁**：用命名互斥量 `Global\officeace2api-watchdog` 兜底，
  第二个守护会直接退出，不会两边对打；
- 如果连续秒退（配置写错、语法错误）按 3→120 秒退避，不会 100% CPU 空转；
- 稳定跑满 5 分钟就把退避归零，下次崩溃立刻重启；
- 计划任务带 **登录时自启** 触发器，重启电脑也会回来。

#### 两个已经踩过的坑

**坑一：`-NoNewWindow` 让 node 和守护共用同一个控制台。**
控制台一关或者收到 Ctrl+C，两个**同时**死，守护连 `server exited` 都来不及写——
日志里就是「说了 `starting server`，然后再也没有下文」，退出码 `0xC000013A`
（`STATUS_CONTROL_C_EXIT`）。现在改成 `-WindowStyle Hidden`，node 有自己独立的控制台，
守护能活下来做重启。

**坑二：无条件杀端口占用者。**
原来的 `Clear-Port` 看见谁占着 7864 就杀谁。手动 `service.ps1 start` 一次，
就会出现两个守护轮流杀对方的服务，表现是「服务每隔几分钟就掉一次，又自己回来」。
现在先探健康，活着就不碰。

**坑三：两个实例同时写 `data/`，把刚轮换出来的 refresh_token 抹掉。**
`refresh_token` 是一次性的，两个进程各拿一份内存里的旧 token 去换，
后写的那个会把先写的成果覆盖掉，表现是「服务好好的，突然要求重新登录」。
现在服务自己带一把 `data/instance.lock`（**单实例锁**）：

- 锁里记 `pid` + 进程启动时间（Win32 `ToFileTimeUtc`），启动时两边都对上才判定「已有实例在跑」，
  直接退出并提示端口被占；**pid 被系统复用**的情况靠启动时间差（>15 秒）区分开；
- 陈旧锁自动接管，不会出现「上次没退干净，这次起不来」；
- 端口被占（`EADDRINUSE`）时打印明确原因、释放锁、退出码 1，交给守护决定重试；
- 正常退出、`stop.cmd` 都会清掉锁文件（`stop.cmd` 兜一刀，防止极端时序下的残留）。

```powershell
powershell -ExecutionPolicy Bypass -File tools\service.ps1 status   # 能看到 payload 是 watchdog 还是裸 node
powershell -ExecutionPolicy Bypass -File tools\service.ps1 log      # 看守护日志
```

#### 端口占用清理（`tools/free-port.ps1`）

**为什么单独抽一个脚本**：端口被占时 node 会**立刻** `EADDRINUSE` 退出，而 `start.cmd`
还要在那边空等 30×2 秒做健康检查，最后只丢一句 `health check timeout`。
对「双击了没反应」的新用户，这就是一个黑洞。所以启动前先把端口这件事说清楚。

三条启动路径（`start.cmd` / `run-bg.cmd` / `run-foreground.cmd`）、`service.ps1 start`、
以及守护进程的 `Clear-Port` 现在**共用同一份判断**，不再各写一套：

| 端口上的情况 | 处理 |
| --- | --- |
| 空着 | 继续 |
| 占着但 `/healthz` 不通（多半是没退干净的上一个实例） | 杀它，连子孙一起；如果被杀的是我们自己的实例，再把守护一起停掉，免得它立刻又拉一个来抢 |
| 占着且 `/healthz` 通，但响应体不是本服务 | 当普通占用者处理（打印程序名 + pid 后杀掉） |
| 占着且是本服务的**健康实例** | 一个字节都不动，直接用 |
| 落在 Windows **保留端口范围**里 | 没进程可杀，直接给出 `net stop winnat` / 换端口两条路 |

几个真跑出来的结论（静态看代码看不出来的）：

- **保留端口范围在系统里会表现成 `pid 4 (System)` 在 LISTEN。** 实测本机 `8030`、`8999`
  既是 `netsh interface ipv4 show excludedportrange protocol=tcp` 里的保留段，也各有
  一条 `System` 的监听项。第一版把它当成「普通进程占着、需要管理员权限」，
  提示用户去任务管理器结束 `pid 4` 结束 —— 谁也不该被这么教。现在先认系统进程，
  再走「保留范围」这条解释路径，并给出两条真正能用的办法。
- **`netstat` 看不见保留范围，只有真绑一次才知道能不能起来。** 所以判断分两步：
  先看有没有监听者，再在目标地址上真 `bind` 一次；而且第一次严格绑（和 node 一样），
  失败后再用 `SO_REUSEADDR` 宽松绑一次 —— 严格失败、宽松成功说明只是 TIME_WAIT
  之类的残留，放行；但如果端口上还挂着内核的监听项，那宽松成功只是假象，不放行。
- **探活必须短超时。** 占着端口却不应答的东西（裸 TCP 监听）会一路卡到超时，
  第一版 3 次 × 5 秒，双击 `start.cmd` 之后要**发呆 20 秒**才开始干活。现在 2 次 × 2 秒。
- **子进程里不能 `&` 调用它。** 脚本结尾是 `exit`，`& script.ps1` 里执行到的 `exit`
  会把**调用方**一起结束 —— 守护进程会直接死掉。所以 `service.ps1` / `watchdog.ps1`
  一律用 `powershell -File` 起**子进程**再用 `$LASTEXITCODE` 取结果。
- **认守护进程要看命令行末尾。** 原来的 `-like '*watchdog.ps1*'` 会把「命令行里提到
  这个文件」的任何 shell 都算进去（写测试时真把自己的终端杀了一次）。现在要求脚本
  路径是命令行**尾部**：`[\\/]watchdog\.ps1"?\s*$`。
- **守护进程也必须挑 Node ≥ 20。** 这台机器的 PATH 里是 `C:\nvm4w\nodejs\node.exe`
  （v14.21.2），而 `src/*.mjs` 用了 `||=`，于是 `node` 秒退——语法错误、退出码 1、
  日志里只有「`server exited code=1 after 0s`」，看上去像服务自己崩了。而
  `find-node.cmd` / `service.ps1` 都有版本门禁，只有守护进程漏了，还只找
  `<盘符>\OfficeAce\...`（本机实际在 `D:\软件\OfficeAce\...`）。结果是**计划任务这条路
  永远起不来**，手动双击 `start.cmd` 却一切正常。现在守护进程的解析顺序和版本门禁
  跟另外两处对齐了。

日志：每次动作都写进 `logs\port-clean.log`（自己按 1 MB 滚一代，因为没人会去管它）。

```powershell
powershell -ExecutionPolicy Bypass -File tools\free-port.ps1            # 按 config.json 的端口清
powershell -ExecutionPolicy Bypass -File tools\free-port.ps1 -Port 7864 # 指定端口
powershell -ExecutionPolicy Bypass -File tools\free-port.ps1 -RepairNat # 保留范围时自动重启 winnat（要管理员）
powershell -ExecutionPolicy Bypass -File tools\free-port.ps1 -Force     # 连健康的实例也让路（慎用）
```

退出码：`0` 端口可用、`1` 清不掉、`2` 清不掉且需要管理员权限（`free-port.cmd` 拿这个码去提权）。

回归测试：`node tools/test-free-port.mjs`（8 项）。它**真起进程**来验那两条相反的硬要求：
死占用必须被清掉（并且清完端口真的能绑）、健康实例必须一个字节都不动（进程还在）；
另外钉住"保留端口范围要解释而不是教人杀 pid 4"和"探活要快（< 15s）"。

### 附带：积分熔断

号池选号现在会看一眼余额。**余额见底的号在冷却期（默认 10 分钟）内不再被挑中**，
省得每个请求都撞一次 403 再重试。两条安全阀：

- **读不到额度时不熔断** —— 查不到余额不代表不能用，绝不因此拦下请求；
- **全都见底时仍返回一条** —— 宁可试一次，也不要直接 503。

面板「号池」页的凭据行会显示 `积分熔断` 标记；`credits.cooldownOnEmptyCreditsMs: 0` 可关掉。

## 七之六之二、换电脑：整包导出 / 导入凭据

换电脑以前只有两条路：在新机器上把每个号重登一遍，或者手工去 `models.json` 里抠
`api_base` + `Authorization` 一条条填。前者要密码、要短信；后者只能转发，积分读不出来。

现在做成一件：**旧机器导出 → 拷一个文件 → 新机器导入**。

```
双击 export-accounts.cmd   → accounts-backup\officeace2api-accounts-<机器名>-<时间>[-locked].json
双击 import-accounts.cmd <把文件拖到窗口里>
```

面板上等价：「账号池」→「导出凭证」；导入在「导入账号」弹窗底部「从文件导入」那一行。
命令行也行：`node tools/export-accounts.mjs --pass 口令` / `node tools/import-accounts.mjs <文件> [--pass 口令] [--check]`。

### 一、搬的是什么

| 内容 | 从哪来 | 为什么要带 |
|---|---|---|
| 账号档案 | `data/oauth-accounts.json` | 长期 Basic 鉴权 + `baseUrl`，没有它新机器连转发都做不到 |
| `refresh_token` | 同上 | 新机器能继续换临时凭据（**不用重登**）的关键 |
| DPoP 私钥/公钥 | 同上 | 换令牌时要用私钥签 proof，缺了照样得重登 |
| 24h 临时 AK/SK | 同上（`credential`） | 带了就不用等第一次续期；**快过期的丢掉**（见下） |
| 续期链 | `data/refresh-state.json` | `diskTokenUsed` / `rotatedToken` / `deadTokens`，决定会不会重发一个已经被服务器拒过的 token |
| 别名 / 停用 / 顺序 | `data/accounts.json`（元数据，不含凭据） | 新机器不想再改一遍名 |
| 扫盘发现的号 | `accounts.mjs` 的扫描结果 | 本机装过 OfficeAce 就有的那些号 |

`data/` 下的三个文件都是**明文**（我们不像 OfficeAce 那样用 DPAPI 加密自己的数据；
`node tools/diag-portability.mjs` 会把这件事量出来：明文 JWT 几条、DPAPI 密文几条），
所以搬运包必须自己加密，否则等于把长期凭据明文丢在 U 盘里。

### 二、格式与加密

```jsonc
{ "kind": "officeace2api/accounts-bundle", "version": 1,
  "createdAt": 1760000000000, "source": "HOST\\user", "appVersion": "2.3.0",
  "stats": { "total": 3, "renewable": 3, ... },
  "accounts": [ { "id", "label", "kind", "baseUrl", "authorization",
                  "refreshToken", "dpopPrivateJwk", "dpopPublicJwk",
                  "credential", "refresh": { ... }, "disabled" } ],
  "warning": "refresh_token 是一次性的……" }
```

加口令后换成信封格式（**整个 body 加密**，外层只留 KDF 参数）：

```jsonc
{ "kind": "officeace2api/accounts-bundle", "version": 1, "encrypted": true,
  "cipher": "aes-256-gcm", "kdf": { "name": "scrypt", "N": 32768, "r": 8, "p": 1, "maxmem": 134217728 },
  "salt": "…base64", "iv": "…", "tag": "…", "ciphertext": "…" }
```

- **AAD 绑了 `kind/version`**：改版本号或换用途，解密直接失败，而不是解出半截垃圾；
- **口令不落盘**：忘了就只能回旧机器重导（或重新登录）——这是有意的；
- **`scrypt` 参数写在文件里**：以后调强/调弱，老文件照样能解（参数跟着文件走）。

### 三、合并规则（这台机器上到底谁说了算）

导入不是"覆盖"，是**合并**。四条规矩，每条都是为了不制造 `STS5.1806`：

1. **本机有活链，就不采纳包里的链**。`局部活链 = 有 rotatedToken 且没在 deadTokens 里且没标 broken`。
   否则两台机器的链会互相踩（各自拿着对方的"下一个 token"去换，服务器两边都拒）。
   结果里标 `kept-local-chain`。
2. **本机链已经断了（`broken`），就采纳包里的** —— 这正是"用新机器救回来"的场景，同时把
   `broken/brokenReason/brokenAt` 一起清掉。
3. **`deadTokens` / `consumed` 取并集**。宁可多记一条黑名单，也不要少记一条 ——
   少记的后果是重发一个已经作废的 token，直接 1806 需要重登。
4. **能不能写成完整档案，看能力不看 `kind`**：`refreshToken && dpopPrivateJwk` 两样都在才写进
   `oauth-accounts.json`。扫盘发现的号也可能带着这两样（凭据来自本机安装文件），
   这种号在新机器上就该是完整档案，不该降级成"只能转发"。剩下的进 `meta.imported`。

### 四、踩到的五个坑

**① `refresh_token` 是一次性的 —— 导出等于搬家，不是复制**

同一个 token 被两台机器轮流使用，后用的那台会拿到 `STS5.1806`，**两边都得重新登录**。
所以 CLI、面板、文档三处都写了同一句话：导出后请在旧机器上停掉这些号。
想两台机器同时用同一个号，就各自登录一次（两条独立的授权链）。

**② 服务在跑的时候别直接改 `refresh-state.json`**

`RefreshState` 启动时把整个 `refresh-state.json` 读进内存（`this.doc`），之后每次续期
`_migrate()` + `save()` 都是**整份重写**。这时外部写盘 = 马上被内存里那份覆盖掉，
而且不报错。所以导入有两条路，绝不混用：

- 服务在跑 → 走 `POST /admin/api/accounts/import-bundle`（改内存 + 落盘，一个事务）；
- 服务没跑 → 才直接写文件（先备份到 `data/import-backup-<时间>\`）；
- `instance.lock` 里的 pid 还活着、但 `/healthz` 不通 → **直接报错让用户先停服务**，
  不猜它到底是不是在退出中。

这个问题和「七之三之十三」里那条是同一个坑（服务在跑时改状态文件），这次提前避开了。

**③ 把包导回导出它的那台机器，会多出"假身份"**

第一版实测就中了：包里每个"没有 refresh_token 的号"都会往 `meta.imported` 里塞一条，
于是扫盘能发现的号在面板上就有了**两个身份**。看着一样，但 `remove()` 的判据是
`sources.length === 1 && sources[0] === 'imported'` —— 该能真删的会变成只能忽略。
修法：`mergeBundle` 接受 `knownIds`（本机号池现有的 id 集合），已经能发现的号只标
`already-present`，不登记。

**④ `kind: 'manual'` 不等于"不能续期"**

见上面第 3 条规矩。第一版用 `e.kind === 'oauth'` 判，结果实测导出时 3 个号里有 1 个
带 token + DPoP 却被标成"只能转发"。判据换成能力以后，同一台机器导出的包从
"2 个能续期"变成"3 个能续期"。

**⑤ 拖错文件要有能看懂的报错**

`data/accounts.json` 里**只有别名/启停，一条凭据都没有**。用户最可能拖错的就是它。
所以 `parseBundle` 认三种输入：搬运包 / 老格式的 `data/oauth-accounts.json`（按档案导入，
并提示"没带别名/启停"）/ 其它 JSON（明确说"这是 accounts.json，里面没有凭据"）。
空文件、非 JSON、更高版本的包也各有专门的话。

顺带：`AES-GCM` 的认证标签让"文件被记事本另存过 / 传输坏过"变成一句
「口令不对（或者这个文件被改动过）」，而不是解出一堆乱码再报一个奇怪的错误。

**⑥ 端口上活着的，可能不是你这个目录的服务**

这条是做「模拟新机器」时才暴露的：把 git 跟踪的文件拷到一个空目录（等于 `git clone`），
在里面跑 `import-accounts.mjs` —— 它探 `127.0.0.1:7864`，而这个端口上正跑着**另一份项目**
（本机原来那套）。于是它高高兴兴地把账号包 POST 过去，回来的是一句
「管理员 token 无效」：既没导进目标目录，也把凭据发给了别的实例。

修法是让服务"报户口"：`/healthz` 带上 `root`（代码根目录）和 `pid`，
两个 CLI 拿到后跟自己的 `ROOT` 比对（统一分隔符 + 小写），不一致就**不走接口**、
直接读写本项目的数据文件，并打印
`注意 : 127.0.0.1:7864 上是另一个目录的服务（D:\...）`。

两个细节：

- **字段只在本机访问时给**（`remoteAddress` 是 `127.*` / `::1` / `::ffff:127.*`）。
  安装路径 + pid 不该被公网上的探针顺手抄走；监听 `0.0.0.0` 的机器尤其。
- **老版本服务不带 `root` → 当作本项目**。否则升级到一半的机器会突然全部降级成
  "离线读盘"，导出拿到的是磁盘上的旧状态（少掉最新一轮续期换来的 token）。

顺带发现另一个坑：新加的文件忘了 `git add` 时，`tools/diag-fresh-clone.mjs`
（它用 `git ls-files` 精确模拟 `git clone`）会直接报
`ERR_MODULE_NOT_FOUND: src/bundle.mjs` —— 也就是**别人 clone 下来服务起不来**。
这个仿真就是为这种"本机好好的"问题准备的，加新文件后先跑一遍。

### 四之二、备份不许无限堆着（顺带）

这个功能一路都在**造凭据副本**：导出写一个包（明文或加密），导入前又在
`data\import-backup-<时间>\` 存一份快照。都是"含凭据的文件"，但用户不会记得清 ——
和 `server.log` 只涨不滚是同一类问题（那个坑在上一章修过）。

规矩照抄日志滚动：**只留最新 3 份**。两个细节值得说：

- **按 `mtime` 排，不解析文件名里的时间戳。** 文件名被改过好几轮（`-locked` 后缀、
  机器名里本身带横线、`officeace2api-accounts-<机器>-<日期>-<时间>` 拼起来很脆），
  而 `mtime` 永远是真实年龄。同秒内连导两次（`mtime` 一样）时按名字倒序兜底，
  免得"排序不稳 → 把刚写出来那份删了"。
- **导出侧默认只列不删。** 删别人盘上的文件是有代价的：那份包可能正是他准备拷去
  另一台机器的唯一副本。所以不加 `--prune` 就只打印
  「这个目录里还有 N 个旧搬运包（里面就是凭据）」，要不要删由人决定。
  导入侧没这个顾虑（快照是刚自动生成的、内容等于当前状态），所以直接清。

判错的后果很不对称：多留一份只是占地方，删错一份就是"导到一半发现文件没了"。

### 四之三、非交互环境别弹资源管理器（用户截图问上来的）

`tools/export-accounts.mjs` 在 Windows 上会 spawn 一次
`explorer.exe /select,<文件>`，替双击 `.cmd` 的用户把刚导出的包"选中"，省得自己找路径。
这个贴心动作的第一版写成了：

```js
if (flag('--open') || process.platform === 'win32') { … }
```

也就是**只要在 Windows 上就弹**。于是 `tools/test-backup-prune.mjs` 在临时目录里跑它时，
桌面上弹出一个资源管理器窗口；用例跑完立刻把临时目录删掉，资源管理器找不到路径，
甩出一个「位置不可用 —— 如果该位置位于这台电脑上，请确保设备或驱动器已插入…」的报错框。
用户截了张图问"这个是什么问题"。

它还连带一个更隐蔽的后果：资源管理器占着 `accounts-backup\` 这个句柄，
`fs.rmSync(SIM)` 删不掉，而用例的 `catch {}` 把错误吞了 ——
于是 `%TEMP%` 里悄悄留了一份（假的）凭据副本，正是这个功能一直在防的事。

修法是先问一句"有人看着吗"，纯粹到可以单元测试：

```js
shouldRevealInExplorer({ explicitOpen, explicitNo, platform, isTTY, env })
```

- 终端里（双击 `cmd` / 正常开个窗口跑）→ 弹，贴心照旧；
- 管道、计划任务、测试里（`stdout.isTTY` 为假/未定义）→ 不弹；
- `--open` 明确点名 → 管道里也弹；`--no-open` 或 `O2A_NO_OPEN=1` → 一票否决。

**结论**："只在 Windows 上"从来不是判断条件，"有人在看"才是。

验证用的是 A/B 对照，因为"没弹窗"本身没法证明（可能压根没跑）：
先用 `Shell.Application` COM 数"指向探针目录的资源管理器窗口"当尺子，然后
`--open` 跑一次应开出 1 个（证明尺子和开窗能力都正常）→ 关掉归 0 →
默认跑一次是 0 个。实测 `0 → 1 → 0 → 0`，才算把这条焊死。

### 四之四、档案里的 refresh_token 死了，导出该挑哪一份

用户的号池里有个号续期链断了（`STS5.1806`，日志里 `临时续期失败`），
顺手把"导出到底带的是哪份 token"查了一遍 —— 查的过程本身走了两步弯路，都值得记：

1. 先看 `account.refreshToken`：全是空的，以为"扫盘不给 token"。
   实际它挂在 `account.profile.refreshToken`（就是 OfficeAce 自己存储里那份），
   **字段找错了**，结论也就反了。
2. 再对比指纹：档案里 `2673…`、profile 里 `5b8d…`，以为"客户端手里那份是活的，捡回来就能续"。
   翻 `refresh-state.json` 才看到 `deadTokens` 里正好躺着 `5b8d…` ——
   那份我们**试过、被服务器拒了**。所以不是"有份更好的"，是"三份全用过"。

由此定下的导出规则（`collectAccounts` 的 ① 分支里，档案号那条路）：

- 默认照抄档案里的 `refreshToken`；
- 只有**同时**满足下面三条，才改用扫盘（profile）那份：
  ① 本机这条链判了死（`broken`）**且**手里没有下一份（`rotatedToken` 为空）——
  自己还能续就别去动客户端的链，否则等于把客户端的 token 烧掉；
  ② 扫盘那份不在 `deadTokens`／`consumed` 里（换过去照样 1806 就没意义）；
  ③ 扫盘那份不是我们已经在用的那份。

好处是搬机器时不用为一个"其实还能救"的号白重登一次；坏处也用测试钉死了
（`顺手把客户端的活链烧掉` 那条用例就是防这个）。

顺带一个操作事实：面板的「重新发现凭据」走的是 `/admin/api/refresh` → `requestRediscover`，
它只**发现账号身份**，不搬 `refresh_token`。所以链断了点它没用 —— 要么让客户端继续当链的主人
（服务每 45 秒扫一次会跟它的 profile 凭据），要么在面板上对那一个号重新登录一次。

## 八、常见问题

> **一轮系统排查修掉的东西**（都是靠真跑出来的，静态看代码看不出来）。
> 详细过程写在对应章节里，这里只列结果：
>
> | 症状 | 根因 | 现在 |
> | --- | --- | --- |
> | 非流式请求偶尔返回**空回复**、`usage` 全是 0，但明明记了成功 | 预读上游时 `decoder.push()` 一次吐出好几个事件（上游常把 role/content/usage/`[DONE]` 塞在同一个 TCP 包里），代码在**第一个**有数据的帧上就 `return` 了，同批剩下的既没进 `events`、也已从解码器缓冲切走 | 整批收完再判断，一帧都不丢 |
> | 上游明明报错，客户端却收到 200 空回复，而且那个限流的凭据**不冷却** | 「伪 200」的第二种形态：第一帧正常、第二帧才是 `{"error":...}`。错误存进了 `state.error`，但 `build()` 从来不读 | 三种失败形态（中途 error 帧 / 连接被掐 / 没 `[DONE]` 也没 `finish_reason`）都按失败记，池子照常冷却 |
> | 客户端点「停止」以后，代理还在后台把上游 SSE 读完，白烧 TPM 和积分 | `req.on('close')` 注册在 `await readJson()` **之后** —— 而 `req` 在请求体读完那一刻就 emit 过 close 了（只 emit 一次），监听器永远不触发 | 改挂 `res.on('close')`，而且能区分「客户端走了」和「上游断了」 |
> | 上游中途断流 → 客户端拿到 200 + 半截 SSE，没有 `[DONE]`，一直转圈 | `finally` 直接 `res.end()`，异常路径还会跳过 `handle.cleanup()` | 补一个错误帧 + `[DONE]`；异常转成返回值，池子照实记失败 |
> | 上游 200 之后卡住不吐数据 → 客户端永久转圈，也不重试 | 预读超时被 `break` 掉，落到和「真读到帧」同一个 `return` 形状 | 预读超时明确当失败，走重试/报错 |
> | `n>1` 只返回第一个 choice | 累加器写死 `chunk.choices[0]`，`build()` 也只组装一条 | 按 `choice.index` 分别累积 |
> | 拼错的模型名返回 502 | 注册表不校验，直接当可重试错误连打上游 3 次 | 立即 **404 `model_not_found`**，一次上游都不打 |
> | 一个 `max_tokens:-5` 的错误请求要白重试 3 次、多等 4 秒 | 确定性 400 也被当可重试；`unsupportedParam` 正则里的 `invalid.*(param\|field\|argument\|type)` 会命中「参数值不合法」 | 严格匹配 `unsupported/not support/unrecognized`；400 直接短路，392ms 返回上游原话 |
> | 发坏 JSON 或 `"null"` 给管理接口 → **HTTP 500** | 69 个入口全中：`readJson` 抛普通 Error 被兜底成 500；`JSON.parse("null")` 返回 `null` 后属性访问抛 TypeError | 坏 JSON → **400**（带 `BAD_JSON`），非对象体归一成 `{}`，请求体过大 → 413 |
> | 面板上「按模型冷却」开关改了没反应，要重启 | config.json 里存的是 `credentialPerModelCooldown`，而 `setCooldowns()` 读的是 `perModelCooldown` —— 静默失效 | 两个键名都认 |
> | 面板「测试账号」把会回错误体的凭据报成「在线」 | 判的是 `verdict.kind !== 'error'`，而 `classifyUpstream()` **根本没有 `kind` 这个键** → 恒为 `undefined` → 条件恒真 | 按 `rateLimited/authFailed/badRequest` 合成真实的 `kind` |
> | 公网端点关着 TLS 校验 | `http.mjs` 的 `insecure` 默认值是 `true`，而轮询华为云授权码那处没显式传参 | 默认改 `false`（本机自签的那些调用点本来就都显式传了 `true`）；跨 host 跳转不再转发 `Authorization` |
> | 一次 DPAPI 失败之后**所有**账号档案都读不出来了 | 一个「一置就再也下不来」的 `unavailable` 布尔值，且没有任何地方重置它 | 改成「连续失败计数 + 60s 冷却」，一个坏 blob 不影响别的档案 |
> | 面板「下次到期」显示 1970 / Invalid Date | `Math.min()` 收到空数组返回 `Infinity`，序列化成 `null` | 空数组按 0 处理 |
> | 签到接口的 `firstTimeToday` 永远是 `false` | `beforeRec` 和 `rec` 是同一个对象，先写 `rec.days[day]` 再读它 | 写之前先把判断做掉 |
> | 单个账号反复点「签到」会真的反复打接口 | `claimBonus(accountId, { force })` 的 `force` 声明了从没用过，幂等判断只在 `claimAll` 里 | `claimBonus` 自己也判「今天签过没」 |
> | **点「删除」既没删掉、也没停用，反而会把一个已经停用的号重新启用** | `remove()` 里写的是 `this.meta.disabled.filter((x) => x !== key)` —— 那是 `setEnabled()` 里「**启用**」那一半，方向抄反了 | 见下面「移除一个本机账号」 |
> | 手敲 `http://127.0.0.1:7864/admin/`（末尾多个斜杠）整个面板变成一行 401 JSON | 面板的 `api()` 用的是相对路径 `admin/api/xxx`，在 `/admin` 下解析成 `/admin/api/xxx`；在 `/admin/` 下就变成 `/admin/admin/api/xxx` —— 落到兜底的鉴权分支 | 两条都修：`api()` 统一补成绝对路径；服务端把 `/admin/` 也当成面板入口 |

| 现象 | 原因与处理 |
| --- | --- |
| 浏览器 `ERR_CONNECTION_REFUSED` / `127.0.0.1 拒绝了我们的连接请求` | 服务没在跑。双击 `start.cmd`（或 `install-autostart.cmd` 一劳永逸）。最常见的诱因：进程是在命令行窗口里用 `node src/index.mjs` 起的，窗口一关进程就跟着死 |
| 进程老是莫名消失 | 用 `install-autostart.cmd` 注册计划任务，让 Windows 任务计划服务托管，不再挂靠在终端会话下 |
| 日志里 `SyntaxError: Unexpected token '||='` | 选到了太老的 Node（14/16）。删掉 `data\node.txt` 再启动，`find-node.cmd` 会重新挑一个 ≥ 20 的；也可以手工把 node.exe 全路径写进 `data\node.txt`。**守护进程那一侧也已补上版本门禁**（以前它不看版本、只找 `<盘符>\OfficeAce\...`，于是计划任务永远起不来而手动启动正常） |
| `/healthz` 显示 `credentials: 0` | 本机没有 `models.json`。打开 OfficeAce 登录并发一条消息，再 `POST /v1/refresh` |
| 面板上点「改名 / 停用 / 删除 / 测活」没反应，右下角红字 `缺少 id` | **已修**（`api()` 助手没把 `json` 翻译成请求体，所有 POST 都在发空 body）。如果你的版本还是这样，说明 `src/admin.html` 是旧的——它在浏览器里跑，改完记得**硬刷新**（Ctrl+F5） |
| 地址栏末尾多打一个斜杠 `/admin/`，面板就变成一行 401 JSON | **已修**（面板的相对路径在带斜杠的地址下会多拼一层 `admin/`）。旧版本去掉那个斜杠即可 |
| 点「删除」弹「已移除（已记入忽略名单）」而不是「已删除」 | 正常。这个号是本机 OfficeAce 文件里发现的，删不掉（删了下一轮扫描又回来），所以记进忽略名单——效果一样，而且不动 OfficeAce 的文件。想找回来去「配置」页最下面的「已忽略的账号」点恢复 |
| 点「删除」之后号还在列表里，而且变成启用了 | 老版本的 bug（`remove()` 把「启用」当成了「停用」）。升级到含 `ignored` 名单的版本即可，见「移除一个本机账号」那一节 |
| `429` + `ModelArts.81111` / `81114` | 上游对该模型做了 TPM 限流（多用户共享配额）。等 20s 自动冷却结束，或换 `glm-5.2`、`deepseek-v4-flash-0731` 等其它模型 |
| `401` + `APIG.1009 AppKey or AppSecret is invalid` | 凭据过期/换了网关分片。在 OfficeAce 里重新登录（或重启客户端）触发刷新，本服务 45s 内自动跟进；也可手工 `POST /v1/refresh` |
| 积分页显示「读不到」/ `这个号缺少 security_token` | 该号的临时 AK/SK 过期了（默认 24 小时）。**正常情况下会自动续期**，面板上会标「凭据已自动续期」。若续期也失败，说明 `refresh_token` 也过期了（30 天），去 OfficeAce 重新登录一次 |
| 状态列写「可用 · 待续期」，但积分还是读不到 | 这是**两个不同的凭据**：转发走的是不会失效的 `Authorization: Basic`（`model_app_key:model_app_secret`，写在 `models.json` 里），积分走的是 24 小时的临时 AK/SK。所以这种号**照常能跑模型**，只是积分/签到读不出来。点「导入账号」重登一次就会自动接上 |
| 重登了，积分还是读不到 / 还是提示「refresh_token 已经全部作废」 | 已修。早期版本有三个坑：① 上膛时把**新** token 当成「已经消费过」写进锚点，`pickToken` 于是判 `None`；② 续期成功后没把**轮换出来的** token 回写档案，导致第二轮就原地断链；③ `diskTokenUsed` 被轮换值带偏，每轮都触发一次多余的「重新上膛」，90 秒烧掉 5 份一次性 token。三条都补上了，并且 `/admin/api/credits/refresh-credential` 每次都会自己判断要不要上膛 —— 重登之后几秒内自动恢复，不用重启。回归测试：`tools/test-rearm-chain.mjs`（36 项） |
| **导入账号走完了，日志也写了「自助登录完成」，但列表里什么都没多** | 已修。那个号之前在**忽略名单**里（你点过删除），而 `scan()` 里每个调用点都会拿 `ensure(id)` 挡一道，被忽略的 ID 一律跳过 —— 于是刚登录进来的号被立刻抹掉。现在 `attachOauthAccount()` 会把同一个 ID 的 `ignored` / `disabled` 一起撤掉并落盘。<br>语义上也该这样：**用户亲手登录一次，就是最明确的「我要用这个号」**。忽略名单是给「扫盘扫出来、你不想看到」那种准备的，不能反过来把用户的显式操作也挡掉。原来的别名会保留。 |
| 面板点「续期凭据」提示 `STS5.1806 the refresh token has been used` | `refresh_token` 是一次性的，说明用的那份已经被消费过了。**新版会自动换用下一份**（磁盘那份 → 轮换那份 → 放弃）；只有两份都作废了才会明确提示「需要重新登录一次」，不会反复撞同一个错。如果提示就是这个，去 OfficeAce 重新登录，或用面板的「自助登录」重新授权一个号 |
| 续期按钮点了没反应 / 提示跳过 | 当前凭据还有效（剩余 > 10 分钟）时会主动跳过，省下一次性的 `refresh_token`。想强制换就传 `{"force": true}` |
| 一键签到提示「今天已经签过了，没有新的积分可领」 | 正常。同一个活动每天只能领一次，重复领不会加分，返回的列表不变 |
| 签到返回 `500 OfficeAce.11020001` | 请求没带 body。这个接口**必须**带 `Content-Type: application/json` 且 body 给 `{}`——官方的调用点省了 body，但那样会被服务端判错。本服务已经按带 body 的方式发 |
| 积分页显示 `APIG.0624 Unsupported signature algorithm` | 网关只认 `V11-HMAC-SHA256`，说明签名走错了分支。确认 `src/quota.mjs` 里 `/v1/subscription*` 用的是 `signV11` 而不是 `signV4` |
| 积分显示的总数比预期少 | 已过期（`expired_time` 早于当前时间）的套餐条目和奖励活动**不计入**。每日签到类奖励每天 23:59:59 清零重发，属于正常 |
| 明明没怎么用，积分一直在掉 | 查「近 30 天消耗」的走势条和「今天」那一列，配合「调用记录」页对照是哪个客户端在刷。也可以停掉某个号，只留主力号 |
| 某个号突然不出话了 | 看「号池」页该行有没有「积分熔断」标记——余额见底会被冷却 10 分钟。看 `logs\server.log` 里的 `积分余额偏低` 告警 |
| 服务半夜自己死了 / 端口不通 | 现在不会了：计划任务的载荷是 `tools\watchdog.ps1`，进程没了 4 秒内自动拉起。用 `service.ps1 log` 看守护日志；`service.ps1 status` 的 `payload` 一行会告诉你守护装没装 |
| `service.ps1 status` 显示 `payload: node.exe directly (no auto-restart!)` | 计划任务是旧版装的。跑一次 `service.ps1 install -Autostart` 换成守护版本 |

| `404 Model not found` | 上游没有这个模型，`GET /v1/models` 看准确 ID（大小写敏感，例如 `Kimi-K2.6` 与 `kimi-k2.6` 是两个） |
| 客户端连不上 | 确认监听地址是 `127.0.0.1`、端口没被占（现在启动前会自动清，见「端口占用清理」；手动清用 `free-port.cmd`）；客户端填的是 `http://127.0.0.1:7864/v1` |
| 双击 `start.cmd` 没反应，或窗口一闪就没了 | 以前最常见的原因是端口被占：node 秒退 `EADDRINUSE`，`start.cmd` 还在傻等 60 秒健康检查。现在启动前先跑 `tools\free-port.ps1` 把端口清干净（健康的实例不动），清不掉会直接把「谁占着 / 该点哪里」打出来。全过程见 `logs\port-clean.log` |
| `free-port` 说端口落在「保留端口范围」里，杀进程也没用 | 那是 Hyper-V / Docker 的 WinNAT 预留段，范围内谁也绑不上。以管理员身份 `net stop winnat && net start winnat`（或双击 `free-port.cmd` 自动提权重试），或者把 `config.json` 的 `listen.port` 换一个 |
| 模型"卡住"很久没首字 | 上游大模型首字延迟 2~15s 属正常；`deepseek-v4.1-flash` 这类带思考的模型更慢 |

## 十、注意事项

- 默认只监听 `127.0.0.1`，本机自用。要给别人用得改 `listen.host` 为 `0.0.0.0`，**同时务必**
  把 `apiKeys` 换成随机长串，否则别人可以白嫖你账号的额度。
- 上游额度是跟着 OfficeAce 账号走的，别拿去做高并发压测，容易把账号打限流。
- 凭据存在 `models.json` 里，本服务只读不写，不会影响 OfficeAce 客户端本身。
